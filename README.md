# MC 技术执行项目

本项目用于将蒙卡业务脚本封装为独立 MCP 服务，并通过终端智能体调用工具、诊断日志、查询资料和确认修改输入文件。适用于业务脚本接入、开发联调、跨机器部署及合同验收准备，在通用 MCP 工具包与纯净 Harness 基础上增加项目能力。

主责范围为四项智能助手、业务脚本的 MCP 封装及接口对接。专业脚本、核数据、真实算例和参考答案尚待业务方交付，当前工程样例用于验证运行机制。

MCP 与 Harness 仍是独立组件：`mcp/` 可以单独部署给其他兼容宿主；`harness/` 可以连接其他标准 MCP 服务。在本项目把它们组合起来，是一种使用方式，不构成协议或运行绑定。生产使用其他宿主时要配置该宿主自己的修复确认策略。

## 主要功能

| 功能 | 当前能做什么 |
| --- | --- |
| 工具服务与接入 | 独立 Python MCP 服务、工具发现和调用；复用函数、程序、HTTP 接口适配方式接入业务 |
| 终端智能体 | 配置模型与 MCP 服务，以自然语言调用；也可用 `/tools`、`/call` 无模型联调 |
| 日志诊断 | 读取日志、返回命中行及规则建议；真实专业规则待业务审定 |
| 确认修复 | 展示修改计划和 diff，终端人工确认后写入；保留备份，拒绝失效或重复计划 |
| 本地知识查询 | 检索 TXT/Markdown，返回原文与位置；官方资料及参数解释待接入 |
| 基准算例目录 | 查询 CLEAR-S、17×17 等算例的材料状态；真实执行与结果校核待接入 |
| 模型配置与备用 | JSON/环境变量配置模型，符合切换条件时自动使用备用；机制已用受控模型测试 |
| 验证与交付 | 一条命令运行工程测试；生成可复制部署的源码包、文件清单及校验值 |

## 按验收推进

下一步先接入一个真实业务脚本，完成“直接运行对照 → MCP调用 → 自然语言调用 → 诊断、确认修复与专业校核”，再扩展四项助手和共性验收。开发与测试入口：

- [验收导向开发计划](docs/验收导向开发计划.md)：阶段、责任、材料依赖、当前待办及每阶段通过条件。
- [测试与验收说明](docs/测试与验收说明.md)：现在可执行的测试命令、终端演示、真实业务/两宿主/模型/指标/72小时验收方法，以及证据和交付位置。
- [实施边界与验收入口](docs/实施与验收.md)：现有工程基础与合同条款对应。

计划和说明是内部执行文件；真实材料、正式测试计划确认及甲方见证结果到位后才能形成合同验收结论。当前 `verify.sh` 重跑MC项目30项工程测试，历史摘要还包含通用包测试，二者统计范围不同。修改Harness源码后先构建再测试，具体见测试说明。

## 本机快速开始

### 前置条件

| 条件 | 本机现状 | 说明 |
| --- | --- | --- |
| Node.js 22 | v22.22.1 | `harness/terminal.mjs` 已打包依赖，直接可跑；只有改 Harness 源码才需要 `corepack pnpm` |
| Python 3.10+ | 3.14.4 | `mcp/start.sh` 首次运行自建 `mcp/.venv` 并按 `requirements.txt` 装依赖，需要网络；离线部署用 `WHEELHOUSE=<wheel目录>` |
| 模型密钥环境变量 | 已配置 | 只放在本机环境变量里，不写进项目目录；见下「模型凭据」 |
| MCP 服务在运行 | 用前自检 | 每次使用前先启动（下面第 1 步），`/health` 返回 200 才算就绪 |

#### 模型凭据（本机已配好；换机器要重做）

Harness 只从环境变量读密钥，**不读 `.env` 文件**（`harness/lib/config.mjs` 只查 `process.env`）。本机已配置两处：

```text
~/.config/mc-tech-execution/env    # 权限 600，导出 MC_PRIMARY_API_KEY / MC_FALLBACK_API_KEY
~/.bashrc                          # 一行 source 上面这个文件，新开终端自动生效
```

换到另一台机器时，把下面两行放进该机器启动终端时会执行的脚本（例如 `~/.bashrc`）即可，密钥值找项目负责人要：

```bash
export MC_PRIMARY_API_KEY='<主模型密钥>'
export MC_FALLBACK_API_KEY='<备用模型密钥>'   # 可以与主模型同一把
```

注意两点：环境变量只对「设置之后新开的终端」生效，当前终端里要先 `source ~/.bashrc`；缺少密钥时终端会直接报 `未设置模型密钥环境变量：MC_PRIMARY_API_KEY`，按这个名字补上即可。

#### 环境自检（约 10 秒）

```bash
node --version                                                          # 需要 v22.x
python3 --version                                                       # 需要 3.10+
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8770/health    # 需要 200
echo "${MC_PRIMARY_API_KEY:+模型密钥已设置}"                              # 需要输出「模型密钥已设置」
```

#### 常见失败与对应动作（报错原文为本机实测）

| 终端里看到 | 原因 | 怎么办 |
| --- | --- | --- |
| `未设置模型密钥环境变量：MC_PRIMARY_API_KEY` | 当前终端没加载密钥（环境变量只对新终端生效） | 新开终端，或 `source ~/.bashrc`；确认 `~/.config/mc-tech-execution/env` 还在 |
| `[失败] MCP mc: fetch failed` | MCP 服务没在运行、端口不通 | 回到第 1 步跑 `mcp/start.sh`，用 `/health` 确认返回 200 |
| `bash: ./harness/run.sh: No such file or directory` | 站在 `harness/` 目录里用了项目根的相对路径 | 先 `cd ~/projects/mc-tech-execution` 再执行 |

### 三步上手

第 1 步，终端 A（保持运行）——启动 MCP 服务：

```bash
cd mcp
./start.sh
```

默认监听 `http://127.0.0.1:8770/mcp`。启动脚本首次创建本目录虚拟环境并安装 `requirements.txt`。通过 `/info` 查询服务及工具定义；正式发现和调用使用标准 MCP。

第 2 步，终端 B（**在项目根目录执行**；不要 `cd harness` 之后再敲 `./harness/run.sh`）——先确认工具连通：

```bash
cd ~/projects/mc-tech-execution
./harness/run.sh --prompt '/tools'
```

出现「已连接 1 个 MCP 服务，发现 7 个工具 + 4 个本地工具」说明服务与注册表都对。这一步同样会加载 `model.local.json`，所以也要密钥已就绪；只有在没有该文件的副本（例如打包分发出去的包）里，这一步才是完全免模型的。 

第 3 步，同一个终端进入对话：

```bash
./harness/run.sh
```

不用加参数：`run.sh` 发现同目录有 `model.local.json` 就默认加载它。这个文件是本机默认工作配置，端点和模型已经填好，**不需要 `cp model.example.json`**；换端点或换模型也只改它一个文件，想临时改跑另一份配置时才写 `--config 路径`。

`model.example.json` 是发给别人的通用模板（端点只是格式示例，未验收），不要拿它覆盖 `model.local.json`。分发出去、不含 `model.local.json` 的副本会自动退回环境变量模式（`MC_PRIMARY_*` / `MC_FALLBACK_*`）。

`/tools` 和 `/call` 不需要模型；自然语言需要项目许可的实际模型服务。模型支持JSON配置、环境密钥、主备配置及兼容本地HTTP API。日常入口、取消行为和日志说明见 [Harness 手册](harness/README.md)。

### 试一句

> 查看 examples/error.log，给出错误提示。把 examples/input.txt 中的 -1 改成 100，先显示修改内容。

工具参数里的路径相对 `workspace/`，所以上面两个文件实际是 `workspace/examples/error.log` 和 `workspace/examples/input.txt`（`examples/` 目录只放演示说明）。

修复工具使用单处精确文本替换；需要用户在真实终端输入 `yes` 后才写入。`no`、预览变化、文件已变和非交互输入都不能完成修改。演示完整步骤见 [修复演示](examples/修复演示.md)。修改后仍需调用专业校核工具，当前没有它。

对话里除了上面 7 个 MCP 工具，还有 4 个本地工具 `read`、`bash`、`edit`、`write`：只读的 `read` 直接可用；`bash`、`edit`、`write` 每次都要你在终端输入 `yes` 才执行，非交互场景一律拒绝。它们的工作目录是**项目根目录**（`--cwd` 可改），与 MCP 工具相对 `workspace/` 不同——同一个输入文件，MCP 工具写 `examples/input.txt`，本地工具写 `workspace/examples/input.txt`。改项目输入文件仍优先走 MCP 的预览→确认链，因为它多了 diff、哈希校验和备份；细节、安全边界和收窄办法见 [Harness 手册](harness/README.md)。

## 远程与已有工具接入

将 `mcp/service.config.json` 中 host 改为远程监听地址，设置 publicUrl 和服务器环境中的 `MCP_AUTH_TOKEN`；部署细节见 `mcp/README.md`。客户端在自己的注册表填写服务URL及 `Authorization: Bearer ${变量名}` 占位符，并提供对应环境变量。不需要共享文件。公开互联网使用已有 HTTPS 入口。

第三方已有 MCP URL 直接加到 `harness/mcp-servers.json`；工具名可作白名单，参数定义由服务发现。普通HTTP接口还需要输入输出契约，再通过通用模板适配。跨机器网络、代理、证书以及真实第三方宿主仍需在实际部署环境验收。

## 现在能验证什么

- 真实 MCP 工具发现、查询、错误返回和部署信息；两种通用模板的函数/程序调用另有独立验证。
- 本项目实际文件的修复计划、终端拒绝不改、同意后一次写入、备份、文件变化拒绝。
- 主模型请求失败后切备用，取消不切换，已有输出时停止且不重放；使用受控模型测试。
- 日志规则提示、文本资料查询及带明确缺料状态的CLEAR-S目录。

仍需业务方提供真实日志、原始脚本、官方资料和算例；还未证明完整四项业务、两个国产实际模型、两个独立宿主、性能指标或72小时稳定性。逐条对应与职责见 [实施与验收](docs/实施与验收.md)。

## 验证与打包：什么时候用

**验证用于检查当前版本是否正常，打包用于保存和分发当前版本。**

| 操作 | 什么时候运行 | 做什么／产物在哪里 |
| --- | --- | --- |
| `./verify.sh` | 修改代码后、准备交付前，或在新环境检查工程行为时 | 安装并检查依赖，运行本项目工程测试；终端显示进度和“校验成功”，详细日志在 `artifacts/` |
| `./package.sh` | 准备交给别人部署、迁移服务器或保留发布版本时 | 整理源码、运行文件、配置、依赖清单、文档和示例；压缩包与校验文件在 `dist/` |

在项目根目录执行验证：

```bash
./verify.sh
```

全部检查通过时，终端会显示：

```text
校验成功：已执行的工程检查均通过，未发现明显问题。
检查范围：依赖一致性、MCP 调用、修复确认、Harness 模型备用策略。
详细记录：<项目目录>/artifacts
```

脚本当前运行30项MC工程测试，不调用外部模型。退出码为0表示本次全部检查通过；中途失败会返回非0，不输出成功提示，按最后显示的阶段查对应日志。它不重建Harness，修改 `harness/cli.mjs` 或 `harness/lib/` 后应先执行：

```bash
corepack pnpm@10.23.0 --dir harness install --frozen-lockfile --ignore-scripts
node harness/build.mjs
./verify.sh
```

打包使用：

```bash
./package.sh
```

生成 `dist/mc-tech-execution-0.1.0.tar.gz`、`dist/MANIFEST.json`（文件清单与哈希）和 `dist/SHA256SUMS`（压缩包校验值）。包中包含源码、固定内核、配置、依赖清单、模板快照、资料、文档和示例；虚拟环境、node_modules、运行日志、本机模型密钥配置和业务中间文件会被排除。接收方解压后按本README安装依赖、配置服务与模型，再启动使用；包不是预装全部依赖的离线环境。

打包不会自动运行验证，也不会修改源码或替你部署服务。同名包会被覆盖，保留发布版本时先保存旧包及其证据；修改默认业务配置时先判断是否适合分发。测试证据位于 `artifacts/`，不包含在运行部署包中，需要另行归档和交付。

推荐交付顺序：修改代码 → 必要时构建 → 验证通过 → 打包 → 在目标环境解压、配置、启动并验证。验证后接着打包可以运行 `./verify.sh && ./package.sh`，前一步失败时不会继续打包。工程验证与打包完成后，合同验收仍需真实业务对照、宿主/模型兼容、指标及72小时等证据，具体执行见[测试与验收说明](docs/测试与验收说明.md)。

## 维护与扩展

接新脚本主要改 `mcp/tools.py` 与业务实现；接知识资料放入 `knowledge/` 并记录版本与来源；算例到位后更新 `config/cases.json` 并实现实际执行/校核。更新通用模板时按 `mcp/UPSTREAM.json` 对照版本，重新运行项目集成测试，避免覆盖项目业务函数。表5-1文档的既有草稿只作输入，正式结果需根据本轮代码及实际业务验收补写。
