MC工具包部署与接入

管理员准备计算环境与标准MCP服务；使用者取得地址并完成连接，然后进入计算流程。

初次安装配置与数据CAD与报告标准MCP服务宿主接入示例配套Skill运行维护

1．准备计算服务器

服务端使用Linux/WSL；Windows可作为MCP客户端。准备Python 3.10+及venv、Bash、C++编译器/make、curl、tar/bzip2与软件源网络。初配会在包内下载运行时及数据，先检查可用磁盘；官方核数据展开约6GB，OpenMC、CAD、Office和计算产物另计。

quickstart 会检查 OpenMC 环境的 include/eigen3，缺失时补装 eigen=3.4；C++ 自定义源编译依赖它。使用 --openmc-prefix 指向自备环境时，需自行保证该目录存在，否则对应例题会在 compile 步失败。

# 在完整源码包根目录执行：
df -h .
./quickstart.sh
./mc.sh call openmc_environment '{}'
./mc.sh call openmc_storage_report '{}'

quickstart准备接口环境mcp/.venv、OpenMC 0.16.0、图表/报告依赖、官方核数据和默认CAD/Office可选组件，生成本机config/openmc.local.json。不修改shell配置或安装系统包；首次下载需要网络。已准备过的服务器先探测再决定是否补装。

已有OpenMC、只需基础计算或另选安装目录
./quickstart.sh --openmc-prefix /opt/openmc-env --skip-cad --skip-office
# /opt/openmc-env须有bin/python和bin/openmc；换成实际环境目录。
# 在本包内新建另一个运行时而保留旧环境：
./quickstart.sh --openmc-prefix .runtime/openmc-new --skip-cad --skip-office

--skip-cad跳过STEP转换环境，--skip-office跳过PDF/DOC转换；普通建模、PNG、Markdown和DOCX仍各依赖其相应Python包。选择会影响可用功能，不能以接口层安装成功认定求解环境已就绪。

2．配置位置、核数据与生效方式

配置选择与生效
工作区CLI --workspace > MC_WORKSPACE > 包根目录 workspace/。本页不改根目录；如已设置环境变量，以探测结果为准。
OpenMC 运行配置CLI --config > MC_OPENMC_CONFIG > config/openmc.local.json > config/openmc.json。其中命令数组、超时等由部署者设置。计算记录保存当次配置。
MCP 监听和鉴权见部署配置，修改后重启服务；直接 CLI 不需要这一层。

若更换工作区，请在新 Bash 会话开始时导出绝对路径 MC_WORKSPACE，后续每一步用同一配置。不要把客户端本地目录当成远程服务端路径。

环境探测中api_available、executable_available、openmc_version_matches应为true，workspace为实际服务器绝对路径。cross_sections_configured只表示当前环境变量状态；不能单凭该字段判断实际核数据齐备，连续能模型还要做API/语义校验并确认HDF5文件可访问。

核数据索引、真实数据及燃耗链

OpenMC引擎安装本身不带核数据；本包quickstart另调用安装器准备official-endfb-vii.1。cross_sections.xml索引与它引用的HDF5都需存在。部署配置可指定cross_sections或受管库，模型材料显式声明的截面索引优先；相对路径基于模型目录。缺失显式路径不能悄悄退到其他库。

燃耗另需链文件，由配置depletion_chain指定或在核数据目录查同名文件；quickstart的核数据安装步骤不包含燃耗链。按所选链的许可和来源部署，不把换库或补链当成原结果可直接复现的保证。

引擎构建、环境探测及跨机比较
openmc-0.16.0-dagmc_nompi_py312h63f0379_103
             └┬──┘ └┬──┘ └┬─┘
              │     │     └── 绑定的 Python 版本（3.12）
              │     └──────── mpi / nompi：是否支持分布式并行
              └────────────── dagmc / nodagmc：是否支持 CAD 几何

三条判断，直接影响能不能做某类功能：

  • nompi 不影响 Slurm 单节点提交（可用 OpenMP 线程 + srun），只影响多节点与并行 I/O。
  • dagmc 构建包含 CAD 几何能力（openmc.DAGMCUniverse）。quickstart默认准备独立cad_to_dagmc转换环境，支持--cad-only补装和--skip-cad跳过；STEP转换与DAGMC建模是不同层，部署时分别检查。调用关系与验证边界见CAD输入流程。
  • 构建串只是声明。CAD 能力是否可用，必须用最小算例验证，见下节。

OpenMC 的功能是编译期开关组合出来的：OPENMC_USE_OPENMP 默认开、OPENMC_USE_MPI 默认关、OPENMC_USE_DAGMC 默认关、OPENMC_USE_LIBMESH 默认关。装了一个 OpenMC 不等于能力齐全。

以上是本包默认路线；实际可用能力以部署的构建与探测为准。源码编译/MPI需要一致的编译器、HDF5、h5py等依赖；不为连接服务器就随意更换锁文件。跨机比较还应记录种子、线程、编译选项和核数据，不能只比较输入文件名或要求所有环境比特一致。

环境返回cross_sections_env_set表示进程环境变量；旧cross_sections_configured保留相同含义。nuclear_data给出部署候选library/source/index_path/index_exists，false的环境变量不表示没有受管库。索引存在仍不证明HDF5齐全，模型显式索引也可能覆盖它。

3．按任务准备可选依赖

默认准备接口、OpenMC/核数据、CAD转换和报告环境。CAD独立环境固定Python依赖版本，原生库在项目内解包；安装器会实际读取STEP、转换H5M并检查尺寸与指纹，通过后才发布CAD配置，不执行系统安装或修改shell配置。

已有基础环境，只补CAD时运行：

./quickstart.sh --cad-only --openmc-prefix .runtime/openmc
# 旧CAD环境与固定依赖不匹配时，保留它，另选新目录：
./quickstart.sh --cad-only --openmc-prefix .runtime/openmc \
  --cad-prefix .runtime/cadenv-new

--cad-only不重复下载核数据或准备Office。完整安装可用 --skip-cad跳过CAD；这样已有OpenMC流程仍可用，CAD转换须另行配置。固定CAD环境约2GB，实际占用随平台与软件包变化；初配需软件源网络、APT元数据及 curl/dpkg-deb，原生库自动准备面向Debian/Ubuntu。它不是已经做过断网安装演练的离线包。

默认探针与示例STEP随源码包提供。示例输入位于服务端 workspace/examples/cad/cube.step；使用自定义 MC_WORKSPACE时，先把输入复制到该工作区。远程MCP不会自动上传客户端的STEP文件。

报告转换

Markdown无需Office，DOCX使用Python依赖；PDF和真实Word97 DOC需LibreOffice和字体。默认quickstart会准备；已跳过时按环境选择配置office_command/font_path，或重新运行完整quickstart补齐，不使用改扩展名冒充格式转换。

CAD运行流程见使用手册CAD入口；报告生成与数据选择见结果章节。

配套Skill：让智能体按任务组织工具调用

先连接MCP，再让宿主加载随包的 openmc-workflows技能。它教智能体选择模型入口、发现参数、预览校核、提交跟踪及交付结果。工具本身仍可独立使用，Skill不启动服务、不替用户决定未知物理参数。

怎么加载

  1. 把完整的 skills/openmc-workflows/ 文件夹复制到运行智能体的客户端机器。需要包含SKILL.md和references，不能只拷一个入口。远程MCP不会自动安装本地Skill。
  2. 宿主支持Agent Skills时，将整个文件夹放入该宿主配置的技能目录，按宿主要求刷新发现或新开会话。各宿主的目录和自动加载支持不同；本包不改任何宿主配置，也不承诺DSH自动识别。
  3. 宿主没有技能安装入口、但能读文件时，直接让它读取下面的SKILL.md，并按任务读取所链接参考。无法读本地文件时，向宿主提供技能正文及本任务需要的参考内容；只有MCP工具连接不代表技能已加载。
# Linux / WSL：在客户端持有源码包的根目录执行
# SKILL_PARENT替换为宿主实际配置的技能父目录，先确认它正确
SKILL_PARENT=/path/to/host/skills
mkdir -p "$SKILL_PARENT"
# 已有同名目录时先核对版本，本命令不会覆盖
if [ -e "$SKILL_PARENT/openmc-workflows" ]; then
  echo "同名技能已存在；先核对，不覆盖"
else
  cp -R skills/openmc-workflows "$SKILL_PARENT/"
fi

Windows可用文件管理器把同一完整文件夹复制到宿主配置的技能目录；包在WSL时，先从WSL共享路径打开。具体目录由宿主决定，不把Linux服务端路径当Windows技能路径。

直接试一句话

先读取并使用 openmc-workflows 技能，核对已连接的OpenMC MCP服务。
我想用自己的组件模型，改一项材料密度后看网格通量和报告。
先检查我需要提供哪些文件和参数，说明支持范围，再执行已确认的任务。

只分析已有作业可以说：“使用openmc-workflows，给作业<实际job_id>生成所选通量报告，不重新计算。”若宿主已注册技能，可按它的正常激活方式调用；这里不要求特定平台的斜杠命令。

怎样判断已加载并正确使用

智能体应能说明它选用了哪条入口、缺哪些输入，并调用环境探测；已有模型先发现参数名与单位再修改。缺密度单位、网格或计算条件时应询问，不能照抄固定例题。任务结束给出实际作业、结果选择、告警和产物位置；只分析结果时不提交新计算。技能文字校验和无模型演练不代表DSH/其他宿主的自然语言执行已经验证。

Skill只维护任务选择和跨工具衔接，详细参数以当前MCP Schema为准；完整用户操作仍见使用手册。技能、手册及工具定义随同一源码包交付；升级包后核对本地技能副本，避免旧技能调用新接口。本轮不启用Beta MCP Skills远程分发扩展。

复测：自启待测服务，结束后自动停止

复测用下列入口，不复用8770上的常驻服务。脚本从当前工具包启动随机本机端口、独立工作区和连接文件；先核对实际MCP握手版本、完整工具名称/参数Schema/说明，以及待测源码指纹。不一致立即停止，不执行后续测试。普通部署仍使用下方的服务启动入口。

# 只验证当前包的版本、工具发现和自动清理，不计算、不调用模型
./scripts/test-mcp.sh

# 在该服务上执行组件完整流程；核数据/运行时按前文准备
MC_TEST_OPENMC_CONFIG="$PWD/config/openmc.local.json" \
./scripts/test-mcp.sh -- bash -c 'exec mcp/.venv/bin/python examples/reproduce_public_models.py --model assembly --mcp-url "$MC_TEST_MCP_URL"'

# 工程校验和发布门禁同样使用这个生命周期入口
./verify.sh --tools-only
MC_TEST_OPENMC_CONFIG="$PWD/config/openmc.local.json" \
MC_TEST_CAD_CONFIG="$PWD/config/openmc.local.json" ./verify.sh --release

--后是测试命令；地址从环境变量MC_TEST_MCP_URL获取。不要写死8770或改用其他已运行服务；传入的命令须使用这个地址，入口不能替任意第三方脚本保证它实际使用了哪个地址。包内真实MCP流程另外在自己的实际会话核对版本和完整工具定义。可用--timeout 秒数调整命令时限，默认1800秒；--output 新目录指定新的证据目录，不覆盖旧证据。

默认在artifacts/test-sessions/<编号>/保存receipt.json、server.log、连接文件与workspace/。回执记录实际版本、工具定义及指纹、服务PID、命令退出码、cleanup.verified_empty和port_released；两项清理结果均须为true。输入、结果与日志保留，清理只停止本轮拥有的进程，不删除旧算例、不停止已有用户服务。

DSH人工复测及中断边界

需要人工操作时，可运行./scripts/test-mcp.sh -- bash -c 'read -r -p "复测完成后按回车结束服务："'保持本轮服务；使用打印的随机地址在独立测试连接中重新发现工具，避免复用旧会话缓存。结束后回到该终端按回车或Ctrl-C，入口自动清理。默认30分钟到限也会清理，长测试先调整timeout。MCP直接发现通过不能证明DSH当前会话已刷新；宿主需重新发现，核对本轮回执中的工具名称和参数说明，再开始操作。不需要修改模型配置。

正常结束、命令失败、超时、SIGINT/SIGTERM/SIGHUP都会清理本轮服务及脱离进程组的计算后代；清理失败会报非零退出并写回执。SIGKILL、系统崩溃或断电无法执行清理代码，不能宣称这些情况下自动清理；若回执缺失或清理字段不为true，先查回执PID和实际端口，不得把本轮记为通过。只处理能确认属于本轮的进程。

4．提供标准MCP服务

完成环境安装与探测后，在工具包根目录启动服务；MCP计算教程在服务启动并发现工具后进行：

./mcp/start.sh

默认地址为 http://127.0.0.1:8770/mcp，传输为 Streamable HTTP，提供本包注册的全部工具。它调用的实现、参数校验和工作区与 CLI 一致；服务不需要 Harness 或模型账号。

启动输出只打印服务名与版本、MCP 地址、传输协议、鉴权方式、内置工具数量和事件日志路径；connection.json和宿主示例按需查文档。若输出缺少地址/传输信息，先核对启动的是不是当前版本。

另开终端，在包根目录用标准 SDK 验证发现和一次调用：

mcp/.venv/bin/python examples/mcp_client.py --url http://127.0.0.1:8770/mcp
mcp/.venv/bin/python examples/mcp_client.py --url http://127.0.0.1:8770/mcp --tool openmc_environment

第一条应返回工具列表及参数 Schema；第二条的 structuredContent 应含实际环境探测结果，isError 不应为 true。探活、协议成功和实际计算是三件事；还可将公开例题 demo 加 --mcp-url，复用同一工作流验证远端计算。

把服务独立于DSH会话运行

前台./mcp/start.sh只在其进程和终端持续运行时提供服务。DSH会话内启动的后台作业不作为跨会话托管方式；一次性的wsl.exe命令、nohup或setsid是否存活，还受宿主进程管理影响，不能仅因启动命令返回就认定常驻。

WSL短期试用：在独立Windows Terminal打开交互式Ubuntu终端，进入包根目录运行./mcp/start.sh，并保持窗口开启。DSH只连接它，不负责启动；DSH退出后，再从另一个PowerShell检查/health。窗口关闭、WSL终止或机器休眠后的可用性要重新检查。

Linux长期运行：systemd用户服务模板

先完成quickstart，确认systemctl --user可连接用户管理器。模板只启动已安装的Python/server，不在重启时安装依赖。当前8770若被已有终端或DSH作业占用，先核对归属，在维护窗口迁移；不能再起一个同端口服务。

mkdir -p ~/.config/systemd/user
cp deploy/mc-tools.service.example ~/.config/systemd/user/mc-tools.service
# 编辑文件：将所有@PACKAGE_DIR@替换为实际安装的绝对目录；含空格等特殊字符须按systemd语法引用。
nano ~/.config/systemd/user/mc-tools.service
systemd-analyze --user verify ~/.config/systemd/user/mc-tools.service
# 确认旧服务已按维护安排退出，再启用：
systemctl --user daemon-reload
systemctl --user enable --now mc-tools.service
systemctl --user status mc-tools.service --no-pager
journalctl --user -u mc-tools.service -n 50 --no-pager
loginctl show-user "$USER" -p Linger

需要注销后继续运行时，由具备权限的部署者按环境政策执行loginctl enable-linger "$USER"，再验证重新登录/断开后的健康状态。可选环境覆盖放在~/.config/mc-toolkit/service.env，路径见模板；令牌只放受限配置文件并设置600权限，不写入共享文档。

模板显式使用KillMode=process，只停止MCP主进程，以保持“停止接口服务不取消已提交计算”的现有语义。这不是systemd推荐的一般默认：子作业会超出服务正常停止清理范围，仍须按job_id查询、取消并确认终态。停机和WSL关闭不承诺保留运行任务。

停服/撤销托管：systemctl --user disable --now mc-tools.service；它不等同取消作业。变更源码后由部署者安排systemctl --user restart mc-tools.service，再复查健康、工具发现与代表调用；让DSH等宿主重新加载/连接MC插件取得最新tools/list，工具数量相同不代表参数Schema已经刷新。按DSH参数定义刷新步骤检查当前会话。本轮提供的是模板和方法，不是已启用的托管实例。

依据：loginctl用户驻留与systemd停止进程规则。

WSL需先具备systemd支持；Microsoft官方说明明确systemd服务本身不会让WSL实例持续存活。它能管理服务，不代替Windows/WSL实例生命周期安排；长期对外服务优先部署到持续在线的Linux服务器。

远程监听与鉴权

例如在计算服务器上设置以下环境；路径、域名和令牌须由部署者替换：

export MC_WORKSPACE=/srv/mc-data
export MCP_HOST=0.0.0.0
export MCP_PORT=8770
export MCP_PUBLIC_URL=https://mc.example.org/mcp
export MCP_AUTH_TOKEN='部署方生成的令牌'
./mcp/start.sh

通用服务在它自己的目录执行 ./start.sh，按自身配置选择端口。非回环监听须有实际 publicUrl 和 Bearer；公网 HTTPS、防火墙、DNS 和代理由部署环境落实，代理保留 Host/Authorization。客户端的环境占位符是否展开，由其自身支持决定。

交给调用方的信息

必须交接怎么用
实际 MCP URL例如同机 http://127.0.0.1:8770/mcp；远端使用可达的真实地址。不要交 0.0.0.0 或另一台机器的 localhost。
传输与鉴权Streamable HTTP；如有 Bearer，告诉对方认证头配置方式，真实令牌另行提供。
服务别名与工具说明别名由客户端区分服务；连接后 tools/list 自动获取工具名和参数，不用手抄所有函数。
数据和产物约定OpenMC 的 case_dir 相对服务端工作区，文件保存在服务器；通用工具的文件输入输出需由其业务接口明确。

启动成功后生成的 connection.json 和受鉴权保护的 /info 是交接辅助。连接文件停服后仍存在；/health 只探活。它们不是所有平台统一的配置文件，按客户端要求填写 URL/认证头即可。Codex/DSH 等宿主示例是可选扩展。

计算结果怎样回到客户端

调用openmc_list_artifacts取得实际path，使用标准MCP函数预览和按需下载；不新增浏览器页面或HTTP文件接口。数据流、宿主客户端准备及Windows/Linux命令统一见使用手册：文件交接。SCP/SFTP或WSL共享目录仍可作为已有替代通道，SSH隧道本身不传文件。

5．宿主接入示例（DSH）

Windows DSH：选同机或远程连接

WSL同机：直接用http://127.0.0.1:8770/mcp。自有Linux服务器：本页采用SSH隧道，不把无认证回环服务暴露到公网。在PowerShell单独开窗口，替换登录用户和服务器地址，使用现有获授权的SSH身份：

ssh -N -L 8770:127.0.0.1:8770 linux-user@server-address
# 保持该窗口开启；若本机8770已被占用，停止本步骤并请管理员协调端口。
# 另开PowerShell：
Invoke-RestMethod http://127.0.0.1:8770/health

隧道的登录认证由SSH负责；DSH仍连接本机8770。若使用已有HTTPS/Bearer网关，按远程部署说明和所用DSH版本的认证配置接入，本页不猜测插件的令牌字段。

确认DSH当前profile后，备份%USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml，将以下patch追加一次，保留原模型配置：

- insert:
    - id: mcp-openmc-forge
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: openmc-forge
        transport: streamable-http
        url: http://127.0.0.1:8770/mcp
        failOnStartupError: true

如已存在同一插件，仅核对地址，不重复插入。DSH监听profile文件热加载；若从WSL写入未触发更新，可在Windows编辑器原样保存一次，再检查插件的连接或加载错误。在工具列表找到mcp__openmc-forge__openmc_environment，只调用它检查环境；找不到工具时先解决连接，不让模型安装包或用Shell替代本次MCP流程。

服务事件日志中的tools.listed记录工具名、数量和连接来源；结合DSH插件状态核对，其他检查客户端也会产生发现事件，不能混当DSH证据。工具注册名通常是mcp__openmc-forge__加原工具名；每个参数的说明由tools/list交给宿主，无需逐个录入函数。

后续表中代码名不含宿主前缀；DSH调用时通常为mcp__openmc-forge__加原名。参数就是表内JSON，工具定义由DSH通过tools/list获取。

检查和调用阶段分别记录：health成功仅表示可达；DSH工具列表出现工具表示发现；实际调用openmc_environment成功后，才进入组件完整流程。不修改已有模型配置，不把自然语言模型的费用视为MCP服务的一部分。

参数说明是否完整：服务端Schema、宿主注册信息、模型看到的简略签名是三层信息。签名未展示某字段，不能单凭这一点判服务过旧；按下方核对，无法观察的层记为未验证。需要重新发现或新开会话时不改模型配置；本包不保证宿主自动刷新。

工具还在列表里，却每次fetch failed

工具列表不证明服务当前在线；failOnStartupError也不是持续健康保证。fetch failed可能发生在建连、传输或响应返回阶段；仅凭错误文本不能断定请求未到达MCP或业务没有执行。先检查实际URL，再检查服务/隧道/HTTP认证，不把所有fetch failed都判成“服务没启动”。

在Windows PowerShell从源码包目录执行scripts/check-mcp.ps1；包在WSL时可经WSL共享路径打开。脚本分TCP连接、初始化和工具发现阶段显示脱敏后的URL：Connection refused表示该端点未接受连接，可能未监听或被拒绝；超时还需查路由/防火墙，HTTP状态则查路径、代理和鉴权。它不调用模型或计算，检查客户端成功也不能代替DSH插件成功。

只有当前地址健康、工具发现及只读环境调用都成功后，才重试尚未执行的任务。提交响应未知时先按原任务名/编号对账，不能因连接恢复就重复提交。

其他宿主：Helix的发现与调用

工具包提供标准MCP，不依赖Helix。将服务地址、传输方式和认证信息配置到宿主后，先执行连接探测并核对工具清单。当前所测Helix版本的API创建连接后，还须单独执行探测；保存连接不等于已发现工具。

本包已提供标准MCP只读注解，但当前Helix对个人外部MCP仍采用保守的高风险分类，不会因注解自动降低授权要求。因此查找这些工具时不要用仅限query的筛选；按原始工具名搜索并精确加载，再由模型填写业务参数。此说明不代替宿主授权，不建议全局关闭审批。

首次使用可以直接说：“用MC工具包的知识检索 search_knowledge 和原文读取 read_knowledge，解释OpenMC的非活跃批次，并引用原文。”例题则先用 openmc_get_official_example 查看输入条件，再经 openmc_prepare_official_example、openmc_run_example_step、openmc_example_status 逐步完成。状态查询可传 wait_seconds:30，避免无休止空轮询；结果与图表/报告的操作见官方例题指南。

宿主具体版本的历史联调和未完成项见项目记录，不要据本页连接方法推断已完成模型联调。

启动快照包括产品Python和模型Schema。漂移或身份不可读取时暂停新操作，查询取消保留；旧服务缺字段时不能记“已匹配”。check-mcp.ps1默认用包内VERSION核对握手版本，也可传-ExpectedVersion；版本不符会给重启指引，不调用模型。

6．服务维护、验证与分发

修改监听地址/鉴权配置后按部署方式重启服务；固定并记录运行配置与工作区来源。

核对运行版本：将本包根目录VERSION与服务实际返回的版本对照。MCP初始化的serverInfo.version、/health.version、/info使用同一启动版本；文件更新不会使旧进程自动升级。MCP环境工具返回service.version及service.version_source=mcp_server_startup，与上述端点同源；openmc_version_matches只检查OpenMC。CLI直接调用不代表在线服务，不返回service字段。MCP环境工具与/info都会返回version_matches_disk、code_matches_disk、changed_files、restart_required和warnings；重启提示出现时不能把旧工具清单当成新版本。旧服务缺字段时，Windows用户可用本页第5节的Invoke-RestMethod查询/health；不能以“调用成功”代替版本核对，也不必一概交管理员。

版本来源与重启未生效时的排查

排除连错目录或旧实例时，由管理员记录监听PID、进程入口/工作目录/启动时间、包版本、Git提交及工作区状态、关键文件修改时间。下面在实际包根目录执行，先从ss结果取得实际监听PID，再替换变量；主机/端口按部署地址调整。

ss -ltnp 'sport = :8770'
mc_service_pid='实际监听PID（替换后再执行）'
ps -p "$mc_service_pid" -o pid,lstart,args
readlink "/proc/$mc_service_pid/cwd"
git rev-parse HEAD
git status --short
stat -c '%y %n' mcp/*.py VERSION

这些是辅助核对证据，不是严格的内存代码证明：时间戳可能保留、部分模块/工作进程可能按需加载，配置和依赖也可能不同。解压源码包没有.git时，Git项记为不适用，改记录交付包的SHA256及包内清单。没有启动时的构建标识，就如实记录证据范围；不能仅凭mtime或版本号写“已证明加载全部当前源码”。本包当前未提供运行源码快照证明接口。

默认配置读取VERSION；wheel读取同源构建的安装元数据，版本在启动时固定。自定义MCP_CONFIG_FILE若显式提供version则采用该配置，应自行保持一致。重启后核对监听PID/启动时间、health版本和一项实际工具调用；旧进程占用端口会使新实例无法监听，不能仅凭启动命令返回判成功。

默认日志上限与作业时限是可调工程配置，容量准入不是运行期硬配额。管理员持续观察磁盘、并发和日志，用户按清理步骤预览并在维护窗口处理终态记录。

完整源码可直接运行或pip install -e .；独立wheel仅包含接口代码，官方资产、知识和环境仍需完整源码包或显式配置，不能以安装后发现工具代替完整部署验证。

分发物：选哪个清单、怎样校验

先选择实际要交付的压缩包，再校验它。package.sh自动生成同版本的三件套：mc-tech-execution-V.tar.gz、mc-tech-execution-V.MANIFEST.json、mc-tech-execution-V.sha256。包内MANIFEST.json对应这个归档，外侧分版清单应与包内一致。dist/MANIFEST.json和SHA256SUMS仅为本机最近一次成功打包的兼容副本，旧目录里可能滞后；不能把它们或文件名排序当作全部历史包的“最新”依据。

在源码包根目录，使用选中的真实路径执行；默认示例随本包VERSION取版本。如果验证的是另一版本，直接换成那一份.tar.gz路径，不改源包VERSION。

mc_package_version="$(cat VERSION)"
./package.sh
./scripts/verify-package.sh "dist/mc-tech-execution-${mc_package_version}.tar.gz"

校验入口不解压、不安装、不调用模型或求解：先比对所选包对应.sha256，再逐项核对归档内文件集合、指纹及VERSION；同名外部分版清单存在时也须与包内一致。成功明确输出“校验成功”，失败非0且说明不一致位置。它只校验所选归档自洽，不证明归档等于当前工作树。交付方须在源码和文档定稿后重新打包，记录源码提交与归档SHA256，并逐文件核对包内内容与该定稿源码一致；定稿后再改文档也应重新发行，不能只推送源码而继续交付旧包。归档自洽不代替verify.sh工程测试、部署检查或专业验收。

下游收到包后，先在三件套所在目录执行sha256sum --check mc-tech-execution-V.sha256（V替换成实际版本），再解压到新目录，按quickstart准备环境；具备源码中的校验脚本时可执行上面的完整归档检查。摘要应来自交付方，校验期间不替换同一归档。

打包先在临时目录完成归档和指纹校验，再发布。普通发布异常会尝试恢复原组合；若回退也失败会非0退出并给恢复材料位置，不能当作成功。掉电或强制终止不具备跨文件原子保证，应重新校验。重打相同版本会替换同名包和清单，需保留旧交付时先归档，源码版本号相同不表示包字节相同。旧版本包不自动删除。

配置怎么填、有什么作用
transport / host / ssh_command通常ssh，host填已有SSH配置别名或user@host；默认BatchMode=yes，复用密钥/代理。local表示工具已在允许访问Slurm的登录节点，不是“模拟HPC”。跳板、MFA、密码登录由运维给出可自动化方案后配置，不在工具内收集密码。
remote_root集群上允许写入的专用绝对目录，每个submission_id建一个子目录；不覆盖其他任务。不需要预先存在该任务子目录。
python_command / openmc_command目标登录/计算环境可用的Python3命令与OpenMC命令数组。远端只运行包内可信辅助代码和管理员配置的求解器；不执行模型携带的Python脚本。先核对OpenMC --version，版本不符就停止。
environment_setup管理员提供的批处理shell语句列表，如module load；用于设置计算节点环境，不接受自然语言临时拼接命令。
cross_sections / path_mappingscross_sections可设远端OPENMC_CROSS_SECTIONS；若XML已写入本机绝对路径，必须在path_mappings给出原引用→集群路径，改动只作用准备副本并返回差异。随模型的直接MGXS HDF5可复制；核数据XML索引不等于整库，需指向集群已部署的库。远端数据完整性/专业适用性仍待真实核验。
commands可选sbatch/squeue/sacct/scancel管理员命令数组，默认同名命令。用于实际集群命令位置或受控测试；不由模型传任意命令。
command_timeout_seconds / transfer_timeout_seconds / max_transfer_bytes默认30秒/600秒/单次2GiB，均可按部署条件调整，不是合同指标。原任务冻结连接/命令/路径身份；当前配置与原身份相同时，运维可调整这三项后对同一编号重试。更换集群不会把旧任务迁过去。

MCP文件交接配置

默认无需新增配置：完整文件5 MiB、ZIP展开/下载文件合计5 MiB、分块256 KiB。调用openmc_file_limits查看实际值。若确需调整，在服务器复制独立示例，不改OpenMC参数或宿主模型配置：

cp config/file-transfer.example.json config/file-transfer.local.json
# 编辑该副本，按磁盘与网络能力调整；例如同时提高max_file_bytes/max_package_bytes
export MC_TRANSFER_CONFIG="$PWD/config/file-transfer.local.json"
./mcp/start.sh

该命令只在由你负责的服务启动环境执行；对已有实例需安排重启才能改变其环境变量。本轮开发验证没有更新用户现有实例。不要照抄配置启动第二个占用相同端口的服务。max_staging_bytes/max_pending_sessions限制未完成上传和下载缓存；min_free_disk_bytes是暂存前的磁盘余量检查，不是整卷配额。preview_text_bytes默认8192（上限65536），preview_image_bytes默认262144（上限1048576），图片超出时仅回元信息；chunk_bytes可调但每帧最多1 MiB，完整文件限额独立可配。

调用方需有本地文件读写/执行能力；只配置远端MCP URL不会自动开放宿主文件。宿主脚本通过同一MCP URL及Bearer传输字节，文件正文不写普通事件日志。未完成编号不失效自动删除，按回执用openmc_close_transfer清缓存，原输入/结果保留。下游第一次使用先完成隔离复测，不复用可能过时的服务。
