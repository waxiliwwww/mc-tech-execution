MC工具包架构说明

这个包把模型准备、输入校核、计算作业和结果整理做成可重复调用的操作。OpenMC负责物理求解，DSH等宿主负责理解自然语言与编排；本包连接两者，保留每次输入、计算记录和产物。用户也可以直接用CLI，不依赖宿主或模型。

甲方技术指引中的OpenMC、DAGMC、CAD转换、Python生成XML和结果解析路线已有对应实现，但并未全部完成。DAGMC用于CAD几何分支；此前演示的公开全堆模型采用CSG几何，所以没有经过它。下文先讲清结构与一条任务，再对照指引说明取舍和缺口。

分层架构输入与CAD路线调用时序结果与文件技术指引对照源码与扩展

1．哪些工作由谁负责

OpenMC的一次计算至少需要明确四件事。核数据库另行提供粒子与材料相互作用的数据；几何图或自然语言描述本身不能替代这些物理输入。

几何

材料放在哪里，例如燃料、包壳、冷却剂与组件布局。

材料

各区域有哪些核素、密度与温度，需有业务依据。

源与运行设置

粒子从哪里开始，采用何种计算模式与统计设置。

计分 tally

要求求解器统计什么，以及按空间、能量等怎样分箱。

统一的是接口与作业记录，分开的是运行环境和职责。接口环境不安装OpenMC；需要它时，api()以JSON启动专用Python进程。长计算则由独立作业进程管理OpenMC可执行程序，MCP服务无需一直占着一次请求等待计算结束。

CAD转换和Office转换使用各自的可选环境，避免复杂依赖都装入接口环境。部署仍需初始化这些运行时与核数据；“独立工具包”指不依赖Helix等其他工程源码，不表示一个没有环境依赖的可执行文件。

2．模型怎样进来，DAGMC在其中做什么

CSG用平面、圆柱、球面及布尔关系描述区域，适合目前的组合建模与公开组件/全堆示例。DAGMC让OpenMC使用CAD导出的网格几何进行粒子跟踪；它负责几何相关操作，物理输运和计分仍由OpenMC完成。DAGMC官方说明。

本包的CAD路径实际调用 CadQuery 读STEP实体，调用 cad_to_dagmc（其网格链使用Gmsh等组件）生成 .h5m，再用 openmc.DAGMCUniverse 加上材料、源和运行设置导出 model.xml。H5M是几何输入，后面的StatePoint HDF5是计算结果，两者不是同一种产物。转换库项目说明。

CAD当前验证与部署范围：代码和既有立方体转换产物证明转换库已使用；另外，官方CAD例题使用现成H5M完成过输运。两段不是同一个输入，不能合称自转换STEP已全链路完成计算。当前快速安装会准备带DAGMC/MOAB的OpenMC，但不安装CAD转换环境；新机使用转换功能前还需单独准备并配置 cad_python_command。复杂工程件的网格质量、单位与材料映射需单独验证。

新模型的组合能力由 openmc_model_capabilities 明确返回：当前支持受控CSG、宇宙、二维矩形格架及部分源/计分类型；它不是OpenMC全部API的等价封装。已有模型可走原生导入路径，自动改参范围则以 openmc_list_parameters 返回为准。服务不执行任意上传Python脚本，也不自动猜专业参数。

3．用户视角：一次任务怎样跨过这些层

输入准备好后，用户先看输入和校核结果，再提交一个有名称的作业。名称用于查找，真正关联后续结果的是 job_id。下面是通用机制，不限于某个固定demo。

提交成功只表示作业已创建。调用方继续用同一ID查询 openmc_job_status，到 completed 后再读结果；失败时查看退出码和日志，取消请求也要查询到终态。服务重启不会抹掉已有作业记录；独立作业能否继续，要看其进程实际状态，不能靠重新提交猜测。

批量扫描在这条链外再包一层：scan_id → 参数组合 → job_id，每个组合先创建参数副本，再使用同一作业管理。当前组合串行执行，不是Slurm集群调度。诊断、资料检索是旁路辅助：工具提供规则匹配或原文，模型负责进一步组织解释；确认修复后仍需校核与重算。

4．结果是谁算的，图和报告怎样对应输入

例如此前的“DSH预备全堆用例”：公开 pwr_core() 几何加8×8×1网格flux计分，经真实OpenMC计算生成StatePoint。openmc_read_results读取keff与计分维度；openmc_plot_mesh提取64格均值、标准差和坐标；openmc_export_report沿用明确选中的计分和筛选，生成报告与完整数据。数据由求解器产生，模型不负责编造数值。

workspace/
├─ 自己的算例目录/               原输入、依赖、来源标记
│  └─ model-spec.json / build_model.py   组合建模时额外保留
├─ .mc-jobs/<job_id>/
│  ├─ job.json / runtime.json     名称、状态、输入指纹、运行配置
│  ├─ work/                      提交输入副本及OpenMC原始输出
│  ├─ solver.log / worker.log    计算与工作进程日志
│  └─ 图、完整CSV/JSON、报告      后处理产物
└─ .mc-scans/<scan_id>/          扫描记录、参数组合和子作业关联

状态记录与输入指纹帮助复查“算的是哪一份”；原始StatePoint帮助核对“数值从哪里来”；图的坐标、计分选择和配套完整数据帮助解释“图画了什么”。默认报告只预览部分数据，完整数据在CSV/JSON。热图展示原始计分分布，不自动做体积、源强或功率归一化；低统计例题不证明专业精度。

返回的 server_path 是服务端绝对位置，同机Windows可通过WSL共享路径打开；MCP不会自动传输模型和大文件。文件打开和维护使用已有存储报告与清理预览；提交前磁盘检查不等于运行期硬配额。

5．技术指引采用了什么，哪些没有完成

依据甲方《OpenMC_MCP_表4-1技术落点对照与开发指引》三页内容：第1页提供参考路线与主要依赖，第2页讨论Python导出XML和分层，第3页讨论开发与文档安排。它不是15项功能逐行的完成清单；合同五类功能的逐项输入、输出与期限仍见合同功能进展表。

指引路线当前采用的方式取舍和实现边界
OpenMC及确定性校验复用官方API与求解器；CLI/MCP共用Schema和业务校核。参考PromptMC校验思路，未依赖其软件包；专业校核仍有适用范围。
DAGMC与CAD转换STEP检查、cad_to_dagmc转换、DAGMCUniverse组装与通用作业。真实调用已存在；自转换件到输运的同输入证据和CAD新机安装未闭环。
Python生成XML、分层运行可信Python API在专用环境生成/读回XML，接口环境无OpenMC。采用运行时API桥，不限于开发期预生成模板；整个部署仍需要OpenMC和核数据。
HDF5与文本结果解析主要经官方StatePoint读取结构化结果；日志用于状态与诊断。优先结构化结果，未把summary.h5、source.h5所有独立操作都封装成工具。
Slurm / HPC目前是本地作业、状态、取消与串行扫描。尚无产品级sbatch/squeue/scancel适配，本地流程不能代替HPC交付。
模型驱动与智能助手提供宿主可调用的建模参数、官方原文检索和有限诊断/修复接口。DSH已发现工具，完整自然语言任务未验证；微调生成、指定基准与专业验收仍未完成。

这里记录工程实现与取舍，不把参考依赖、测试粒子数或“lost particle=0”改成新增合同验收承诺。

6．开发者视角：从哪里修改，怎样验证

修改对象主要入口应一起保留或验证的行为
增加或调整公共操作tools.py、adapters.py；入口为cli.py与server.py。参数含义、类型与输出一致，CLI/MCP共用实现；接口参考从注册表生成。
模型与参数openmc_model_tools.py、openmc_model_spec.py、openmc_import.py。发现、生成、读回与改参同步；保留原模型、源码和依赖，不静默缩减已有输入。
CAD适配openmc_cad.py、cad_worker.py、openmc_worker.py。单位、实体与材料映射、转换输出和OpenMC读入分开检查；真正求解还需完整物理输入。
作业与扫描openmc_jobs.py、openmc_scan.py、owned_processes.py。持久状态、输入快照、失败及取消、只控制自己的进程；当前不含远程调度器。
计算桥与结果openmc_runtime.py、openmc_visuals.py、openmc_reports.py。环境与版本、所选计分/筛选、原始不确定度、坐标、图和报告必须对应。
资料与资源管理knowledge.py、openmc_storage.py、cleanup_artifacts.py。检索返回可追溯原文；清理离线预览并保护关联记录，不自动删除核数据或必要证据。

例题工作流另在 example_workflows.py 接入固定官方目录，复用作业与产物管理；它是检验与学习入口，不是自有模型的唯一入口。扩展测试从实际输入、运行结果或必要失败出发，不能只检查函数存在或文件生成。
