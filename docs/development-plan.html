稳定化阶段原决定（2026-11-08，起点0.14.0 / 175e414，历史依据保留）：MCP工具包独立，DSH/其他宿主组织显式参数，包内Python生成或接入输入；用户无需编写Python。已有脚本为可选入口。自有Linux服务器为计算端；产物服务端保存，依现有文件访问/SCP交接，不新增远程下载。本轮不调用真实模型、不修改模型配置、不更新用户服务。

本轮：宿主与工具服务之间的MCP文件交接

价值：异机时本地路径无法被远端服务读取，结果路径也不会自动变成客户端文件。已有SCP方式需要用户额外操作；本轮用标准MCP函数接通上传→现有模型导入/计算→有限预览→按需取回，让宿主能直接管理文件交接。

已确认范围：只新增MCP函数和宿主侧标准MCP示例，不做浏览器或额外HTTP文件接口，不绑定DSH。宿主需有本地读写或执行能力，二进制分块由程序直传，不经模型复述。默认完整文件5 MiB、可配置，ZIP解压总量也受限；大文件仍可留在服务端计算分析。

完成条件：长度和SHA256通过才发布输入；断线可查同一传输编号及偏移恢复，重复请求不覆盖输入；下载快照、分块和完整文件可核验。用隔离MCP进程验证上传→导入→真实计算→图/报告→预览/下载同源，失败及大小边界不留下半成品。不改已有服务和配置，不调用真实模型；不替代专业验收或真实集群联调。

HPC无账号能先做到什么 · 微调要交什么、怎么做 · 集中确认事项 · 实施顺序与完成标准

HPC方案：无账号先完成适配，真实验收等集群联调

建议先实现一条Slurm通路：MCP工具运行在自有Linux服务器，经集群认可的SSH方式访问登录节点；若允许直接部署登录节点则复用同一调度适配层。已有REST服务的集群可改用slurmrestd，但不同时建设两套后端。用户已确认实施无账号适配；当前transport支持SSH或登录节点local，最终参数以集群条件决定。

M1模型目录 → 预览/校核/输入快照 → 暂存或上传远端目录
→ 渲染批处理脚本 → sbatch → 本地job_id关联cluster_job_id
→ squeue查询排队/运行 → sacct等集群认可接口确认终态/退出码
→ 核对并取回原始结果 → 沿用现有结果读取/图表/报告
取消请求 → scancel → 再查询实际终态

sbatch成功只说明调度器接收，不代表OpenMC完成；Slurm不会自动搬运用户输入和结果，所以目录映射/传输及取回必须由适配器明确承担。远端结果回到本工具服务端之后复用现有读取逻辑；这不是新增面向客户端的HTTP下载功能。

没有甲方账号可先完成如何核对仍不能证明
远端连接配置、资源映射、批处理脚本；复用job_id/任务名/输入哈希，新增远端ID和目录对应。固定输入生成脚本，核对工作目录、命令、线程/资源、输出位置；拒绝未知配置及不完整参数。甲方SSH/MFA、分区、账号和软件模块实际可用。
提交/状态/取消适配、断线后恢复查询、终态和失败分类。使用明确标为替身的SSH/Slurm命令；覆盖排队→运行→完成、失败/超时/取消、squeue消失但终态未知、会计记录延迟。提交回执丢失时先查原任务，不盲重交；不能确认就标未知。真实调度器接受脚本、计费、排队时延和集群故障行为。
输入/依赖暂存、日志回查、结果取回、大小/哈希和来源交接；核数据库默认引用集群已有路径。临时远端目录或受控替身验证输入完整、部分传输不冒充完成、取消不误删输入；取回真实历史结果核对下游读取，说明其不是HPC新计算。甲方计算节点与登录节点共享目录、网络和配额是否满足。

账号到位后必须补：目标集群上的实际小规模模型排队、运行、结果取回及原生值核对；失败/取消和重连查询；按甲方选定的组件或堆芯模型演示。资源先按实际申请，不自行承诺MPI多节点、高吞吐或Slurm数组。查询和取消是远程流程可用性配套，不把它们另造为新增合同数值指标。

鉴权建议：优先复用集群认可的SSH配置/密钥/代理；若只允许密码、跳板、MFA或REST token，则先确认非交互方式。模型不接触密码，凭据不进入工具入参、普通日志或公开包。工具MCP token不等于集群登录凭据。不建设额外用户权限系统。

当前实现与使用入口：Slurm完整工具链；调用/故障/原生结果证据归入同一项目进展。受控调度不替代真实集群。

工作量估计：单一Slurm/SSH路径、复用现有模块的适配与受控验证，约1–2个开发人周；账号/运行环境齐备后另留约3–5个工作日实际联调。是排期估计，不是验收时限；MFA无自动化方式、无共享盘或自定义调度策略会增加工作量。HPC工程难度中等，外部条件风险高。

依据：sbatch、squeue、sacct、scancel、Slurm REST认证说明。目标版本和允许接口仍须集群运维确认。

微调方案：模型生成受控参数，复用Python生成器；训练来源与交付形式需确认

微调是什么：让已有大模型用“需求描述→正确结构化模型参数”的样本进一步训练，调整模型权重；提示词、检索官方文档或普通模型填参本身不叫微调。模型负责理解与映射参数，OpenMC负责物理计算，不能靠模型猜材料、单位或边界条件。

自然语言 + 用户给定文件/物理条件
→ 经确认的微调模型服务 → 受控model-spec
→ 同源Schema/引用/语义校验（缺条件先询问，不代填物理值）
→ 现有包内Python → 几何/材料/设置与源项/tally XML
→ 预览 → 现有分层校核 → 本地或HPC作业
→ 原生结果及来源核对

建议不是让模型直接写任意Python/XML。复用openmc_build_model生成器及Schema，把微调目标收敛为合同所需模型族的需求解析与四类输入参数生成；验收可同时查看模型原输出与最终XML。该实现是否被接受为“基于微调后的大模型自动生成”必须书面确认，不能由开发方自行认定。超出现有model-spec范围的业务需求先列出必要扩展，另行确认，不以Schema限制反向缩减合同。

建议交付对象需要能拿到的内容用途与边界
可识别、可使用的微调模型若项目自行训练：基座模型固定版本/许可、适配权重及配置、推理配置、模型标识。若甲方提供已有模型：确认可用API、精确模型标识、微调来源及使用授权。须证明实际请求使用该模型。只有API时是否满足最终源码/成果移交，要事先确认，不能默认够用。
训练与复现实物（自行训练路线）训练脚本/配置、依赖、数据清单与来源/授权、数据转换、训练日志、权重身份和启动说明。LoRA权重需配套基座版本/获取方式，不能单独当完整模型。让项目能重建/继续维护；敏感资料只在获准环境处理，不上传公开仓库或外部API。
生成接口与工具接入受控参数生成、错误/缺参反馈、模型调用来源、Python输入生成与现有作业交接。统一LLM层的配置切换、密钥和自动主备按原合同实现，不绑定特定宿主。切换到未微调的备用模型须如实标注，不能继续宣称微调生成。至少两种国产API等要求仍保持，验证节点和实际模型由测试计划确定。
生成效果及运行测试材料经确认的需求—参数/输入对照集，独立保留评估集，逐项比较模型输出与预期物理条件，XML读回、实际计算和失败记录。Schema合法/算得出不等于生成正确；不能只检查文件生成。表4-2原指标不变，测试集、公式与阶段应用口径待确认。

数据如何先做：从公开组件/堆芯算例及参数化合法变体生成候选“描述—参数—输入”对照，复用现有真实计算；由专业人员核对单位、材料、源项、计分和边界。训练/评估按模型或参数组合分离，不能把同模板换句话复制进两边；保留缺参、冲突条件和超范围需求，检查明确追问或报不支持。公开数据可启动工程准备，但不能代表甲方业务覆盖或专业参考值。

路线选择：若甲方已有合格微调模型，优先接入并验证；否则建议在经批准的开放权重基座上做监督微调，优先评估LoRA等参数高效方法。它仍会产出真实训练权重，但不保证领域正确。模型规模、训练框架、GPU显存/时间及预算在基座、样本长度和部署环境确定后再估，不先承诺固定GPU型号。合同原文没有独立规定“必须从零训练基座模型”。

难度判断：已有合格模型时，接入工程约3–5个工作日，效果评估和业务整改另计；自行训练时，从数据准备、初版训练到独立评测/整改，先按约3–5个开发人周作有条件估计。难点是合格领域样本、未见需求的参数语义和评估，不是单次训练命令。无专家确认/无模型资源时，12月按原条款验收风险高；若范围、数据、算力现在明确，有机会推进，不能保证日期。上述估计不含排队等待、采购或未知新增模型功能。

技术依据：PEFT LoRA、适配权重与基座依赖格式。工具和训练依赖尚未引入，最终基座和许可需核对。

从现在到12月：执行顺序、验证和完成标准
  1. 先确认最影响工期的条件。本周优先落实验收日期、集群运维联系/接口和微调交付路线、模型/数据/算力负责人。按现有五项表建立首批测试范围，继续使用同一进展入口，不另造台账。
  2. 条件确定后建设两个缺项。HPC先适配和受控验证，同时准备远端模型目录/数据约定；微调先样本与独立评估集，再训练或接入，复用Python生成和校核。业务场景触及现有不支持字段时先提出必要扩展与工作量，确认后实施。
