# 产物在哪里，怎样维护和清理

## 路径到底相对哪里

path、case_dir、series_json/series_csv等工作区路径，相对**服务端MC_WORKSPACE**；默认是工具包根目录/workspace，不相对客户端cwd，也不相对examples/或mcp/。

先调用./mc.sh call openmc_environment查看workspace。图表/报告返回同时带workspace、server_path、location=server；产物清单中的server_path可用于在服务器上打开，directory是记录目录。旧字段path和image保留；image往往只是文件名，优先使用path/server_path。

默认目录示意：

```text
mc-tech-execution/
  workspace/
    cases/或demos/       原算例或演示生成的输入
    .mc-jobs/<job_id>/   单次计算记录、日志、输入快照、原始结果、图与报告
      work/             求解器执行目录；含StatePoint等
      solver.log        求解器日志
      worker.log        监控进程日志
    .mc-scans/<scan_id>/ 扫描记录、基线/组合副本、汇总、曲线与报告
    .mc-plans/          修复计划与关联
    .mc-backups/        修复前备份
```

case.files中的文件名相对case_dir，计算files中的名字在记录work/中，image通常只是当前产物目录内文件名；知识库source是随包资料标识，不按工作区路径解释。优先用server_path或清单，避免只拼某个文件名。

点号开头是隐藏目录，终端用ls -la查看，文件管理器可开启“显示隐藏文件”。目录示意不代表每次都会生成全部文件，清单和实际执行状态为准。

使用openmc_list_artifacts(kind=job/scan, identifier=实际编号)列出已存在的文件、绝对位置、大小和SHA256。大型核数据和输入引用可能位于部署配置的其他目录。当前不提供远程下载，服务端位置不是客户端下载位置。有SSH权限时可用现有SCP/SFTP按返回的绝对路径取回文件；没有相应访问方式时由部署方交付文件，工具不会自动建立下载通道。

## 保留与诊断

先保留出错记录、原输入和专业参考，再整理成功的工程练习。清理计算记录会一并删除其solver.log、输入快照和快照中复制的数据文件、原始结果、图与报告；这些将不能再通过编号查询。

扫描和子计算相互关联。删除单独的子计算会破坏扫描，因此脚本要求按整批扫描清理，或确认该计算没有扫描引用。工作区中的原始cases/、demos/不被自动删除；演示输入也可能已被人工修改，脚本不凭名称猜测可删。

## 清理脚本：先预览，再显式应用

在工具包根目录运行。统一入口为./cleanup.sh，内部调用Python标准库脚本，不需要启动MCP或安装模型；它是服务器本地运维入口，不注册为MCP删除工具。

```bash
./cleanup.sh
./cleanup.sh --scan-id 实际扫描编号
./cleanup.sh --job-id 实际计算编号
./cleanup.sh --older-than-days 7
```

替换示例编号；重复--job-id/--scan-id可选多个目标。未给选择时仅列记录。年龄按finished_at判断，不用文件mtime，按整批扫描选择时连同其子计算。被保留扫描引用的单独子计算不会因年龄条件而被误删。

预览列出将删除的服务端目录及字节数，默认不删。--workspace或绝对MC_WORKSPACE可指定实际数据根。核对并先归档后，在**停止MCP服务及其他CLI写入的维护窗口**，对相同选择加--apply：

```bash
./cleanup.sh --scan-id 实际扫描编号 --apply
```

--apply是永久删除，不承诺回滚。停MCP不会停止独立worker；先查询/取消计算并确认已经结束。脚本拒绝运行、排队、interrupted或缺有效完成时间/进程身份的记录，检查扫描子作业、active_job_id、符号链接和记录锁。中断记录可能存在遗留求解器，首版拒绝自动清理，应先由部署者核对实际进程与记录。

脚本必须在实际计算服务器和相同PID命名空间执行，不能在另一台机器上凭共享挂载的目录判断远端进程。

脚本互斥并在执行前重新检查目标，不能替代维护窗口，也不声称可在线抵抗其他CLI并发改写。发现工作区还有未确认结束的记录会拒绝执行。损坏的关联记录须先核对，不跳过它们来猜测哪些可以删除。

## 修复关联与失败处理

预览发现修复计划引用所选作业时默认拒绝，并列出plan_id。确已归档、接受其后无法查询原失败/重算或继续重验时，可显式加--allow-repair-references；修复计划、备份和修改后的原算例仍保留，但保留它们不等于保住其依赖的计算历史。

操作失败会返回非0；部分删除时分别列出已删、未删或可能部分删除的目录，不报告全部完成，也不自动重算或无条件重试。先读错误、核对实际目录，再决定人工处理。清理后的查询应明确报记录不存在。

外部核数据库、配置、知识库、源码、原业务算例与.mc-plans/.mc-backups不在删除目标内；它们的备份与容量管理由部署方另行安排。日志和计算输出目前不会自动轮转清理，需按使用量定期管理。
