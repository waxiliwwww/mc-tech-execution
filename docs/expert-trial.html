MC工具包专家试用清单

我们提供Linux服务器、工具包和MCP服务，专家连接使用。先用一个专家熟悉的组件或简化堆芯模型，核对输入、计算和结果是否符合其研究意图，再做少量改参及异常验证。此清单用于准备和记录技术试用，不代表已部署、已测试或合同验收通过。

1．试用前准备

负责方准备和核对开始条件
我们：部署与连接冻结代码提交/包校验值；按环境说明部署接口、OpenMC、核数据及所需CAD/报告依赖；核对服务地址、网络可达、鉴权与工具发现。从专家实际使用的客户端完成连接检查。当前没有目标服务器部署成功回执，执行时记录。
我们：资源与文件记录工作区绝对路径、核数/线程和可用磁盘，核对作业时限、单XML大小限制和日志上限；首轮按受控单任务安排。接收专家模型到独立目录，约定产物交接通道。预算适合该模型；文件在服务器可读，专家能实际取得CSV、图和报告。MCP路径不等于上传/下载，现有工具不提供远程下载。
专家：模型与研究问题一个已知可运行的原生OpenMC模型及依赖；版本/核数据、原生运行设置与结果；希望观察的keff/tally、单位、筛选与归一化；一个要修改的参数及允许范围。双方确认当前工具支持该输入和结果类型；缺少资料先记录，不让模型猜物理条件。
共同：判定方式明确参考结果来源、采样/收敛要求、比较容差、专业判定人。我们核对工具与文件交接，专家判断物理适用性；其他材料提供责任由项目落实。没有可靠参考也能试操作，但不形成准确率结论。模板假设与真实业务模型分开。

我们向专家提供实际可达的服务器MCP地址和鉴权方式；连接模板中的127.0.0.1只适用于同机访问，不能原样交给远程专家。远程监听与认证按标准MCP连接说明配置，令牌另行交接，不写入试用记录。

明确参数可以直接经CLI/MCP试用。若计划让专家通过DSH自然语言完成任务，由我们先约定模型测试预算并预演同一入口；工具发现不能代替自然语言全流程验证。HPC不在当前可执行路径内。

2．按同一个模型完成一轮测试

以下复选框仅供现场勾选，刷新不保存；实际结论请写入试用记录。

步骤调用与操作看什么、留下什么
导入模型 openmc_import_model → 预览 openmc_preview_input → 校核 openmc_validate_inputs（按需启用API/语义/几何检查）。核对材料、几何、源、设置和tally与专家原模型一致；保留case_dir、预览文件指纹与校核结果。API能解析不代表物理正确。
命名提交 openmc_submit_job → 状态 openmc_job_status，直到终态。控制版本、核数据、采样设置、种子和线程等比较条件。保留job_id、输入快照、状态和日志；核对提交指纹与所确认输入一致。completed仅为工程执行结论。
读取 openmc_read_results；明确tally/score/nuclide/filter后绘图、导出所选报告，空间结果另用openmc_plot_mesh。对照原生结果与参考，核对值、标准差、维度/坐标、单位和选择。交付配套CSV/JSON及实际图/报告，不只检查文件存在。
发现参数 openmc_list_parameters → 副本 openmc_prepare_case；专家指定两三个取值，用openmc_submit_scan串行执行。原模型保留，修改读回一致；scan_id与各job_id对应，失败/未运行项不隐藏；专业趋势由专家判断。
用独立副本和已约定资源的任务测试取消 openmc_cancel_job，或测试一个已知输入错误；继续查询终态。确认取消请求与完成区别、无继续运行的本任务进程、原输入和首次失败保留。过快完成的任务记“取消未覆盖”，不能算取消通过；不在专家主作业上做破坏性演练。

详细调用方法见模型工作流、计算与结果操作和参数参考。本清单不新增测试阈值。

3．结果怎样判断

  • 工程交接：输入、参数、job_id、原生结果和整理产物关联一致；失败有证据且能说明如何继续。进度百分比和“调用成功”不替代终态及数据核对。
  • 专业结果：用事先确认的参考和容差评价，结合统计不确定度、收敛与归一化判断。没有依据的项记“待专业确认”，不能改成通过或补零。
  • 数据完整性：read_results预览可能截断；明确选择后的配套数据才是完整所选数据。通用曲线与所选报告同源，网格热图当前为独立产物，不自动并入该报告。固定源通常没有keff。
  • 范围：本轮是受控领域技术试用。合同功能、性能、指定基准、宿主/模型兼容与稳定性仍按合同和正式测试计划逐项验收，另见执行对照。

执行中若日志截断、worker丢失、结果缺失或磁盘不足，暂停受影响任务，保留原记录；未知结果先查原编号，不盲目重投。清理先预览，确认维护窗口与证据保留范围后再执行，见产物与清理。

4．每个场景记录这些信息

提交/包版本；客户端与服务器环境；模型及参考来源；case_dir、job_id/scan_id；参数和选择条件；工程结果与专家结论；实际产物位置；首次失败与复测关联。结论区分通过、发现问题、未覆盖、待专业确认，注明判定人和日期。
