# MC 技术执行：实施边界与验收入口

本文保留2026-10-13工程基线及职责说明。下一步阶段和任务状态见[验收导向开发计划](验收导向开发计划.md)，实际测试操作、通过条件和证据留存见[测试与验收说明](测试与验收说明.md)；后续进度在开发计划中更新。

## 本轮约定

用户主责智能助手四项、原始业务脚本的 MCP 封装与接口对接。其他业务模块的专业算法、输入输出正确性由对应业务负责人提供并确认。以终端交互为主；项目文件可整体迁移，除固定 Harness 核心依赖及安装的公开运行时/第三方依赖外，不读取其他工作目录。

本轮先将双语言通用工具包与最小 Harness 固定成可验证包，再在本项目实现不依赖真实蒙卡脚本的通用扩展。完成条件是：一，包能独立部署并通过真实 MCP 发现与调用；二，项目内人工确认及模型备用可被行为测试验证；三，合同每项能定位已实现内容、缺失条件和后续验证。测试 fixture、合成输入和待交材料不得写成真实业务验收通过。

## 项目当前定位

通用协议能力来自本项目保存的 Python MCP 模板快照；项目函数与工具定义放在 `mcp/`。纯净 Harness 的固定 tgz 随 `harness/vendor/` 保存，项目通过公开 API 增加确认与模型备用，不修改纯核，不修改 Helix 工作树。

修复路径为：日志提示 → 生成精确替换计划 → 展示真实 diff → 用户在终端确认 → 执行修复 → 记录前后哈希和备份。文件在预览后变化则拒绝；重复调用已执行计划则拒绝。文本修改不等于蒙卡校核，业务校核脚本到位后需要再接一段校核/重算。

确认策略目前属于本项目 Harness。使用其他 MCP 宿主时必须给 `apply_repair` 配置其人工审批机制；MCP 协议本身不会把工具标注变成权限闸门。服务端仍只接受受信调用者。演示使用专用 workspace，不应让两个独立服务同时修改同一工作目录；跨进程协作及外部编辑器并发写入尚未作事务保证。

## 下一批工作

先取得一个真实业务脚本及正确/错误各一组输入输出，验证直接运行与MCP结果一致，再接入日志诊断、确认修复及校核闭环。随后补资料解析、CLEAR-S及其他算例。测试计划经甲方确认后，再开展真实模型、宿主矩阵、指标与72小时验证。

测试结果见 `artifacts/` 中本次实际生成的记录；文件存在、单元测试通过、模拟模型链路和真实业务验收是不同证据，不相互替代。
