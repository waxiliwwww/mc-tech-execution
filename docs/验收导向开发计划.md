# 验收导向开发计划

这份计划用于安排本仓库下一步开发。推进顺序是：**先确认验收口径和业务材料，再做一个真实业务闭环，随后补齐四项智能助手，最后完成跨宿主、真实模型、性能、稳定性和交付验收。** 每阶段用实际产物和通过条件结束，代码写完不直接等于验收通过。

编制基线：2026-10-13。依据为仓库内[技术规格书提取文本](../references/技术规格书-提取文本.txt)的表4-1、表4-2、表5-1及§3、§4.4—4.5、§8—9；原始DOCX见 `references/`。PDF作为实现参考，不能代替规格书要求。本计划是内部开发安排，甲方尚未确认正式测试计划。具体执行步骤、测试编号和证据格式统一见[测试与验收说明](测试与验收说明.md)。

## 1. 你负责什么，做到哪里才算完成

按当前分工，你主责四项智能助手、原始业务脚本的MCP封装、Harness接入及相关文档章节。其他模块需要你协助对接，但专业算法、蒙卡计算正确性和参考答案需要对应业务负责人承担。这个内部分工不减少合同对整个项目的要求。

| 工作范围 | 你负责交付 | 必须由项目方／业务方提供或确认 |
| --- | --- | --- |
| 错误诊断、交互式修复 | 日志读取、证据定位、建议生成、确认修改、调用专业校核的流程 | 真实错误样本、正确修复方案、输入规范、校核工具及专业结论 |
| 本地知识库 | 文档导入、版本与出处记录、检索、基于原文的参数解释 | 可使用的官方文档与手册、参数解释参考答案及版本范围 |
| 基准例题库 | 算例登记、自然语言选择、调用执行和查询、展示结果 | CLEAR-S等真实算例、运行条件、脚本、核数据、参考结果及容差 |
| 其余表4-1功能 | 按业务接口封装、参数校验、失败回执、部署、自然语言调用联调 | 几何、输入生成、作业、计算、图表和报告等真实业务实现及验收人 |
| 共性能力和技术文档 | 独立MCP部署、宿主与模型接入、取证脚本及智能体章节 | 目标环境、模型权限、宿主选择、总体测试计划确认和项目验收组织 |

合同还明确了输入生成“基于微调后的大模型”。这项成果及模型提供者要在整体项目中落实，不能以通用Harness或提示词配置替代。

### 当前基础与目标差距

当前已有独立MCP服务、固定Harness核心、7个项目工具、文本知识检索、修复预览与人工确认、模型备用策略和工程测试。已有证据见[基线记录](../artifacts/validation-summary.json)。真实蒙卡脚本、官方知识资料和可运行算例尚未接入；`get_case`当前始终返回不可运行，改一个状态字段不能让算例实际执行。

目标是让用户用自然语言完成一次可追溯的业务任务。例如：运行业务算例失败后，智能体根据真实日志指出问题，引用依据，展示输入文件差异；用户拒绝则不修改，用户同意后保存备份并修改；调用业务校核及必要重算，返回新结果和证据。若校核仍失败，要明确失败原因和下一步，不能报告“已修好”。

## 2. 开发边界保持不变

- MCP工具包和Harness包各自独立。工具定义、输入输出和服务发现遵守MCP；`/info`及部署输出帮助人接入，实际工具能力以MCP发现结果为准。
- MC业务增量放在本项目。通用封装方案保留TS、Python两种；合同正式MC服务按规格书使用现有官方Python mcp SDK实现。不要为MC任务把通用包改成专用包。
- Harness纯净核心继续固定版本，通过项目层公开接口扩展。项目交付包不读取开发者其他工作目录，部署环境中的运行时、依赖、模型和远程业务服务要明确列出。
- 当前先保留终端交互。诊断、修复确认、知识问答、算例调用可以用终端证明；合同的两个独立宿主、真实图形/报告产物等仍需各自演示，终端打印“成功”不能替代这些证据。
- 先复用 `mcp/tools.py`、`business.py`、`adapters.py`、`harness/lib/`、`tests/`、`verify.sh`。后续增加测试驱动或导入器只服务明确缺口，不另起一套通用框架。

以下是推进顺序。阶段C与D在首个真实闭环完成后可部分并行；正式指标与稳定性测试应使用已冻结、可复现的候选版本。

| --- | --- | --- | --- |
| A 验收口径与首批材料 | 职责、脚本清单、样本与指标定义，补入既有需求和测试计划 | 本仓库、规格书、业务接口人可用 | 四项主责和其他模块负责人明确；首个脚本能直接运行；95%/90%、样本量、两宿主、模型、72小时负载有确认安排 |
| B 首个真实业务闭环 | 一个真实脚本适配、成功/失败样例、诊断—确认修复—校核记录 | A中的脚本、依赖、输入、参考答案及校核条件到位 | 同一输入直接运行与MCP结果一致；真实模型调用正确；拒绝不改、确认后改、校核结果可核查；T02—T04的首组真实样本通过 |
| C 四项智能助手补齐 | 真实诊断集、专业修复、官方资料导入、CLEAR-S可运行接入 | B通过；各项专业材料到位 | T03—T06覆盖确认的功能用例；业务专家确认诊断、解释和算例结果；不能只测目录查询 |

### A阶段先解决的四个问题

1. **一个脚本怎样算可接入。** 收到源码或入口、运行时和依赖、启动命令、工作目录规则、参数及单位、输入输出样例、正常退出和错误日志、预期耗时。长期任务还需提交/状态/取消协议；只有“程序名称”不够。
2. **结果怎样算正确。** 业务方先给正确样例和参考结果。表4-2要求值95%与说明中物理结果90%的对象、计算方法、容差和统计设置应由双方明确记录，不能自行选较低值。调用成功率的分母、重试和失败分类也要先定。
3. **在哪些环境证明。** 明确两种独立MCP宿主及版本、两个国产API、本地模型、甲方服务器和算力条件。确认主模型流式输出中断时应如何恢复：当前实现仅在尚未输出实质内容时自动切换，已输出后停止，是否满足服务连续性条款需评审。
4. **谁做专业判断。** 为每类脚本、错误诊断、参数解释、基准算例指定业务审定人；为整体合同指定汇总与验收联系人。其他模块未交付时保留“待材料／待验证”。

### B阶段第一批开发要具体做到什么

选择一个耗时可控、有已知正确结果、能构造明确错误并修复的真实脚本。优先选择与输入校核或小算例执行有关的入口，减少对大规模算力的依赖。

| 顺序 | 修改或补齐位置 | 做法及结束条件 |
| --- | --- | --- |
| B1 固定直接运行基线 | 业务适配模块、测试数据与依赖说明 | 在同一计算条件下直接执行，保存输入哈希、命令、退出码、输出和专业参考结论 |
| B2 MCP封装 | `mcp/tools.py`及业务适配实现 | 使用现有函数/固定参数程序/HTTP适配器；明确schema、单位、文件路径、超时和错误。MCP输出与B1对照一致 |
| B3 自然语言调用 | 现有Harness配置和工具说明 | 用项目允许的真实模型完成同一任务；检查实际工具及参数，不只看最终回答 |
| B4 错误到修复 | `config/error-rules.json`、`mcp/business.py`及对应测试 | 将真实日志关联到输入对象/位置；建议经专业确认后生成预览，执行用户拒绝和同意两个分支 |
| B5 修改后验证 | 业务校核/运行接口与结果呈现 | 接入专业校核，必要时重算。保存备份、前后差异、校核和重算结果；失败保留现场，不自动宣称成功或静默回滚 |
| B6 补记录 | `tests/`及当次 `artifacts/runs/` | 可重复运行的集成用例、操作步骤和首份真实业务记录；B1—B5证据能相互关联 |

当前单处文本替换适合验证流程。若真实输入需要多文件、结构化参数或联动修改，再按样本扩展修改计划，明确变更范围和失败恢复；不能直接把字符串替换宣传成通用蒙卡修复器。当前写入保护针对单个服务进程，部署期间应使用独立工作目录，跨进程并发修改仍需另行设计和验证。

### C阶段各能力要补到哪里

| 能力 | 下一步开发 | 通过条件 |
| --- | --- | --- |
| 智能错误诊断 | 引入几何重叠、核素缺失、语法错误等真实日志；从日志证据关联输入位置；补未知错误和无错误样本 | 定位与建议符合专业参考答案；未知错误明确无法判定；有依据，不能把未命中当作输入正确 |
| 交互式修复 | 基于实际文件格式补参数校验、修改预览、专业校核与重算；验证其他宿主的人工审批 | 未确认/拒绝不改；确认绑定真实变更；失效计划拒绝；备份可恢复；校核失败如实报告 |
| 本地知识库 | 按收到的格式建立最小导入流程；保留原文、版本、章节/页码映射；参数解释引用检索依据 | 官方文档和用户手册可检索、可解释、出处正确；不存在的问题不编造。PDF/DOCX是否需自动解析由实际材料决定，人工转换要纳入确认流程 |
| 基准例题库 | 登记真实CLEAR-S及约定典型算例；关联依赖、执行/查询接口、参考结果与验证器 | 自然语言选择正确算例并真实运行、读取结果、按专业判据对照；缺料时明确不可运行 |

对其余表4-1功能，逐个沿B1—B3复用接入方法。长作业采用提交后返回任务ID、再查询/取消的方式；不能依靠同步MCP请求无限等待。可视化与报告接入要保留真实产物并打开核查，不能只返回路径。

### D—F阶段需要补的工程任务

部署验证覆盖“别人独立部署MCP，你用Harness远程连接”和“别人独立部署Harness，连接标准MCP”两种方式。第三方只给普通HTTP地址和函数名时，应先取得请求/响应协议，再走HTTP适配器；已有MCP地址则直接发现和接入，不能把任意URL当作MCP。

测试侧逐步把真实案例加入现有 `tests/`。指标阶段再增加必要的批量执行与统计，稳定性阶段再增加能持续发起业务请求、采集资源和关联结果的驱动；这些驱动目前尚未提供。两类测试都必须输出原始记录，报告数字能回算。

发布时复核代码、打包清单和依赖，冻结源码与部署包哈希。现有 `package.sh` 固定输出0.1.0同名文件，重打包会覆盖旧包；正式发版前需先保留旧版本证据并明确版本命名。`artifacts/`不进入运行部署包，验收记录需要独立交付。通用工具包、Harness核心的来源及使用边界也要在移交清单中保留。

## 5. 材料没到时，先做哪些事

可以继续修复已发现的Harness问题、回归现有工程测试、核对工具说明/错误信息/部署信息的一致性；准备首批脚本的交接清单和验收口径，完善测试用例及证据记录格式。若目标服务器、宿主和允许使用的模型已具备，可提前做连接和配置联调，但这部分不能提前填写真实蒙卡功能结论。

应暂缓批量扩展虚构业务工具、编造CLEAR-S结果或继续堆积只证明加法/占位目录的验收案例。当前最大依赖是专业脚本、样本和判据；先拿到一个完整交接包，会比增加通用抽象更快暴露真实差距。

## 6. 工期与难度怎样判断

目前不具备可靠的人日估算条件：真实脚本数量、输入文件格式、目标环境、算例耗时和参考答案尚未确定。建议D03结束后按“脚本封装、业务适配、测试与取证、文档”分别估算下一批，并把等待材料及算力排队时间单列。

| 工作 | 当前难度判断 | 主要变数 |
| --- | --- | --- |
| 已规范函数/程序的MCP封装 | 中低 | 脚本是否有稳定输入输出、依赖和错误定义 |
| 部署与多宿主、多模型接入 | 中 | 网络鉴权、宿主审批能力、模型工具调用与流式故障行为 |
| 真实诊断和专业修复 | 中高 | 日志能否定位输入对象；正确修复与专业校核是否可程序执行 |
| 知识库解析与参数解释 | 中 | 文档格式、表格公式、版本对应和参考问答质量 |
| CLEAR-S与物理指标 | 高依赖 | 真实数据、核数据、软件环境、算力和物理容差；不是单靠智能体开发能解决 |
| 72小时与正式交付 | 中 | 候选版本稳定性、长作业、资源监测、失败整改和完整重测窗口 |

合同§8以签订日T0安排3/6/7/8个月节点，其中第一批是输入生成及作业管理，智能助手属于第二批。应由整体项目负责人把本计划映射到实际T0；本计划未承诺新的日历工期，也不改变合同节点。
