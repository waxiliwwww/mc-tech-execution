# 测试与验收说明

这份说明供开发、联调和验收执行人员使用：现在先运行现有工程测试与终端演示；业务材料到位后按下列用例补真实证据；正式验收按甲方确认的计划执行。开发优先级和任务状态统一维护在[验收导向开发计划](验收导向开发计划.md)，本文件维护操作、判据和取证方法。

依据：[技术规格书](../references/技术规格书-提取文本.txt)表4-1、表4-2、表5-1及§4.4—4.5、§9。编制日期2026-10-13；**本文件尚不是甲方已批准的测试计划，也不是测试通过报告。** 正式测试前应把实际人员、环境、用例数据、样本量、指标定义补入表5-1测试计划并提交确认。日常开发自测可继续开展。

## 1. 先分清三种结论

| 层次 | 主要回答 | 可以依据的证据 |
| --- | --- | --- |
| 工程测试 | 工具协议、配置、确认、失败处理和独立运行是否按设计工作 | 自动测试、合成样例、本地受控模型、部署搬运记录 |
| 真实业务验证 | 真实脚本、日志、知识和算例是否得到正确处理 | 同条件直接运行对照、真实模型调用、专业参考答案及实际产物 |
| 合同验收 | 全部功能、性能、兼容性、稳定性和交付是否符合约定 | 经确认的测试计划、完整实测报告、甲方见证与专家评审 |

“启动成功”“发现工具”“模型说完成了”“目录里有CLEAR-S”各自只能证明对应现象。验收必须继续查看真实工具调用、输入输出、文件产物和专业判定。

在现有仓库检查当前构建：

```bash

```

迁移后在解压所得项目根目录运行相同命令。正常结束返回0并提示记录位置；非0则检查失败日志。脚本遇错即停，后续套件可能未执行，不能据上次残留日志宣称本次全部通过。

| --- | --- |
| `artifacts/python-dependencies.log` | Python依赖一致性 |
| `artifacts/node-dependencies.log` | 锁定Node开发依赖安装结果 |

### 留存本次运行，防止覆盖旧证据

固定名称的日志会被覆盖。需要保留完整复测批次时，在仓库根目录执行下面的Bash示例。它先保存上一批固定日志，再运行测试；脚本中途失败时，新目录不会混入未执行套件的旧日志。此处只是已有命令的记录方法，没有新增测试工具。

```bash
mc_run_id="$(date -u +%Y%m%dT%H%M%SZ)-$$"
mc_run_dir="artifacts/runs/$mc_run_id"
mkdir -p "$mc_run_dir/previous" "$mc_run_dir/current"
for mc_log in python-dependencies.log node-dependencies.log python-tests.log harness-tests.log; do
  if [ -f "artifacts/$mc_log" ]; then
    mv "artifacts/$mc_log" "$mc_run_dir/previous/"
  fi
done
date -u +%FT%TZ > "$mc_run_dir/started-at.txt"
if ./verify.sh > "$mc_run_dir/verify-console.log" 2>&1; then
  mc_verify_status=0
else
  mc_verify_status=$?
fi
printf '%s\n' "$mc_verify_status" > "$mc_run_dir/exit-code.txt"
date -u +%FT%TZ > "$mc_run_dir/ended-at.txt"
for mc_log in python-dependencies.log node-dependencies.log python-tests.log harness-tests.log; do
  if [ -f "artifacts/$mc_log" ]; then
    cp "artifacts/$mc_log" "$mc_run_dir/current/"
  fi
done
cp harness/BUILD.json "$mc_run_dir/"
node --version > "$mc_run_dir/node-version.txt"
mcp/.venv/bin/python --version > "$mc_run_dir/python-version.txt" 2>&1
printf '测试退出码：%s；记录：%s\n' "$mc_verify_status" "$mc_run_dir"
```

最终判断以 `exit-code.txt` 和实际套件输出为准，不能用上述最后一个 `printf` 的退出码代替。日常快速自测无需每次做完整验收归档，候选版本和重要复测应留存。

终端一启动MCP：

```bash

```

终端二启动交互Harness：

```bash

```

在Harness中逐条输入（下面是终端内部命令，不是Bash命令）：

```text

/call mc__preview_repair {"path":"examples/input.txt","old_text":"-1","new_text":"100"}
```

应发现7个当前项目工具；诊断返回日志证据及“规则提示”边界；预览返回差异和真实 `plan_id`。此时业务输入不改变，但服务会保存内部计划。


第一次确认输入 `no`。在第三个系统终端检查文件仍为原内容；再次发起同一 `apply_repair`，看到重新展示的差异后输入 `yes`，再检查文件：

```bash
cd /home/zhangbolun/projects/mc-tech-execution
cat workspace/examples/input.txt
sha256sum workspace/examples/input.txt
```

通过条件：拒绝后文件不变；同意后变为 `particles = 100`；回执的修改后哈希与实际一致；回执指定的备份保留原内容。再次发起相同 `apply_repair`并经过终端确认后，服务端应拒绝，提示已经执行，文件不再改变。终端不能通过管道、`--prompt`或模型自己写 `confirmed:true`取得人工授权。

继续在Harness内执行：

```text
/call mc__search_knowledge {"query":"particles"}
/call mc__get_case {"case_id":"CLEAR-S"}
/logs
```

知识查询当前只能命中工程说明；CLEAR-S必须显示缺料且不可运行。这两项现象是占位状态如实呈现的工程通过条件，**不满足专业知识库和基准例题的业务验收条件**。

本次工具回执与终端记录在 `artifacts/harness/`，MCP日志在 `mcp/logs/`，计划与备份分别在 `workspace/.mc-plans/`、`workspace/.mc-backups/`。按实际 `plan_id`保存相关文件。自动集成测试会清理临时样例，仅有测试断言日志时，不应声称已归档全部修改前后文件。

## 4. 真实业务怎样测试

下面T02—T12是待落实的验收用例组。它们定义操作和判据，**不是仓库已有同名可执行脚本**。接入实际业务后将可自动化部分加入现有 `tests/`，其余保留人工操作和专业判断。每组覆盖成功样例及关键失败样例。

### T02 原始脚本与MCP调用一致性

对每个业务脚本，固定版本、依赖、输入、工作目录、单位、计算设置和随机统计条件。先直接运行取得退出码、日志与产物，再通过MCP调用同一输入，最后通过自然语言发起同一任务。分别保存原始输出和对照结果。

通过条件：工具和参数选择正确；MCP封装不改变业务含义；业务成功/失败被正确表达；文件产物真实存在且可打开；确定性输出一致，蒙卡随机输出按专业方约定的统计容差比较。进程退出0但缺少约定产物不得算业务成功。补错误参数、依赖缺失、超时及取消场景；长任务记录提交ID、状态、取消结果，客户端取消请求不等于远程计算已经停止。

### T03 智能错误诊断

业务方至少提供覆盖几何重叠、核素缺失、语法错误的真实日志和参考定位，另加未知错误及无错误样本。保存预期类别、原因、输入文件/对象/位置和可接受的建议。测试者让智能体从日志开始独立诊断，再由业务审定人对照参考答案。

通过条件：证据对应真实日志，错误位置和原因正确，建议适用于该输入；不能只匹配关键词或返回日志行号就判通过。信息不足时应说明无法进一步定位，不能臆造输入位置；未知/无命中不报告“模型正确”。诊断质量的量化判据由正式测试计划约定，本说明不另造合同百分比。

### T04 交互式修复

在独立测试工作目录使用已知可修复的真实输入。先预览，再拒绝，比较前后文件哈希；重新发起并同意，核对只发生展示过的修改、备份和日志，然后调用专业校核及约定的重算接口。

必须覆盖：未确认不修改、拒绝不修改、同意后修改一次、计划失效/文件已变拒绝、确认期间预览变化拒绝、重复执行拒绝、越界路径拒绝、校核失败如实报告。多文件或结构化修复在实现后另补对应原子性/恢复用例。恢复备份由明确操作完成，不自动假设已回滚。

通过条件：确认绑定实际变更，文件操作符合计划；已知可修复的正例必须通过约定专业校核。只有预先定义的校核失败、信息不足等反例，才以正确报告未解决状态、保留证据作为该反例通过条件，不能以如实报告失败代替正例成功。每个参与验收的宿主都要验证确认流程。当前MCP服务没有独立的人类身份审批闸门，人工确认由宿主执行；直接调用服务写工具不能被当成“Agent已询问用户”的证据。

### T05 官方知识资料解析和参数解释

收集约定软件版本的官方文档、用户手册及其来源。按实际格式导入，保留原始文件哈希、版本、章节/页码到文本位置的映射。选取常用参数、单位/范围、相似参数、版本冲突和资料未包含问题，由专业人员先给参考答案。让智能体查询并解释，逐条检查引用是否支持答案。

通过条件：实际资料能被解析和检索，参数解释符合该版本原文，引用可回查；无依据时不编造，版本冲突可辨识。PDF/DOCX是可能的材料格式，不是规格书逐字列出的两个必选实现；收到什么材料、采用何种解析流程应在计划中确定。只有把工程说明放进TXT检索不足以通过。

### T06 基准例题智能调用

对CLEAR-S及甲方确认的其他典型算例，准备输入、核数据、执行脚本、依赖、计算设置、参考结果和容差。先证明直接运行可复现，再让用户用自然语言选择算例、确认必要参数、提交、查询完成状态、读取真实结果并对照。17×17性能测试集与CLEAR-S分别留证，不能互相替代。

通过条件：选择与调用正确，任务确实执行，输出来自本次任务，结果满足专业判据；缺数据/依赖时报明确错误，不返回样板物理结果。当前 `list_cases/get_case` 仅查询目录，执行/查询/结果校核工具还需开发，不能在本说明中虚构其调用命令。

## 5. 部署、宿主和模型怎样验（T07—T09）

| 编号 | 执行方法 | 通过条件与证据 |

远程部署按 [MCP手册](../mcp/README.md)使用实际 `publicUrl`和鉴权，核对DNS、HTTPS入口、代理、防火墙及客户端环境变量。`/health`只证明进程在线；`/info`帮助配置，不能替代标准MCP握手、发现和调用。默认本机端口测试不能计为异机部署。

最小Harness与MC Harness源于同一核心，不能自行作为“两个独立宿主”交差。通用MCP包与Harness解耦需要单独证明；MC服务依赖本项目业务文件是正常项目组成，不应误写成可以只拷贝一个 `server.py`部署。

T09还应单独做故障注入：主模型请求开始前/未输出内容时失败，应自动切到备用；用户取消不切换；两个模型都失败要结束并留错；已执行工具不能因切换重复执行。当前策略遇正文、思考或工具调用片段已输出后发生故障会停止，不做自动跨模型续写。应先确认该边界与§4.4“服务连续性”的验收解释；若甲方要求继续恢复，则先开发并补测，再判达标。受控故障实验与正常72小时测试分别进行，避免混淆失败口径。

## 6. 性能指标怎样计算（T10）

在测试开始前冻结数据集、任务文本、模型版本、工具版本、随机统计条件、重复次数、失败分类、参考答案及容差。不能看到结果后删失败样本或修改阈值。先用少量样本验证执行与统计方法，再按甲方确认的样本规模正式测试。

| 指标来源 | 应先确认 | 必须保留的原始记录 |
| --- | --- | --- |
| 表4-2 MCP接口调用成功率≥95% | 总调用的定义、样本量、超时/工具错误/参数错误/取消归类、重试是否计新调用 | 每次调用的任务ID、尝试序号、工具/参数、时间、状态、错误、重试/备用关系；成功数与总数 |
| 表4-2 MCP接口调用结果准确率≥95% | “结果准确”的对象、粒度、计分方式和分母；不是仅看JSON格式 | 每个判定项的输入、参考、实际、判断依据、审定人、通过/失败 |
| 同一条说明中的物理结果准确率≥90% | 与95%的关系；17×17=289栅元测试集组成、关键物理量、参考值、容差、蒙卡统计不确定性及“准确率”公式 | 自然语言输入、生成文件、相同计算设置、运行日志、物理量、参考结果和逐项计算 |

调用成功率可按已确认分类计算 `成功调用次数 / 总调用次数 × 100%`。建议同时报告原始尝试成功率和整项任务完成率，使重试影响可见；后者不能替代合同调用成功率。预期报错的反例单独统计其测试判定，业务调用成功/失败与“错误处理测试通过”是两回事，分母是否包含该类样本由计划预先确认。

95%与90%同时保留，不能自行把二者取平均、选其一或把90%理解成允许10%任意数值偏差。当前没有真实17×17样本和专业口径，不能给达标结论。统计脚本、指标数据集与专业结果比较器需在开发计划D09落实。

## 7. 72小时稳定性怎样验（T11）

正式开始前，计划应确定受测范围（MCP、宿主、模型及业务依赖）、目标环境、调用频率/并发/任务组合、长任务行为、故障定义、监测频率、重启/恢复是否允许以及中断后的重新计时规则。保持进程空闲72小时不等于约定负载下稳定运行；五分钟时间/运行时长输出也不能替代业务调用。

执行顺序：

1. 冻结候选代码、包、配置和测试集，先做短时预演，确认请求确实执行、产物和监测都能归档。
2. 在确认的负载下连续运行72小时，记录起止时间、每次任务和MCP调用、业务输出校核、进程状态、CPU/内存/磁盘、请求耗时及异常。
3. 周期检查证据持续写入并且能关联请求与结果；不能只看进程或心跳。额外响应时间/资源上限若用于判定，应先写入计划，不在结果出来后加标准。
4. 如出现故障，保留时间和现场、受影响任务、原因、修复及复测记录。建议修复后重新跑完整连续窗口；实际计时和判定按甲方确认规则执行，不能把断开的时段拼成“连续72小时无故障”。
5. 输出覆盖完整时间轴的日志、负载与资源记录、调用统计、异常清单和结论，由测试负责人复核。

当前仓库未提供完整72小时驱动和监测采集，也未执行该项。需要先完成D10的工具与环境准备，不能把启动服务后人工等待写成已有自动验收方案。

## 8. 每次验收证据怎样组织

复用 `artifacts/`，正式运行按 `artifacts/runs/<运行编号>/`隔离。这是后续运行时建立的目录约定，不表示现已存在全部材料。每批至少保存下列信息，缺失写明“未采集”，不能以空目录代替记录。

| 内容 | 记录要点 |
| --- | --- |
| 被测版本 | 代码提交或源码清单哈希、部署包SHA256、核心来源、`harness/BUILD.json`、依赖版本；当前核心为带未提交变更的来源构建，沿用实际来源说明 |
| 环境与配置 | 系统/硬件、运行时、MCP地址及服务版本、宿主/模型、业务软件及核数据、配置哈希和脱敏摘要 |
| 输入与预期 | 用例编号、规格条款、任务文本、输入文件哈希、参考答案/结果、计算设置、容差和审定人 |
| 执行过程 | 起止时间、命令或交互、任务/会话/计划ID、工具名和参数、完整回执、退出码、重试和备用事件 |
| 产物与判断 | 输出文件及哈希、diff/备份、业务校核结果、实际与预期差异、通过/失败/阻塞/未执行、执行及复核人 |
| 异常与复测 | 缺陷编号、影响、处理意见、修复版本、原失败记录及复测结果；不覆盖原失败 |

单条记录可直接使用以下字段，不要求另造管理平台：

```text
运行编号／用例编号：
合同条款／业务负责人：
代码或包版本／环境／模型及宿主：
输入与参考依据（路径及哈希）：
预期结果和通过条件：
实际操作与时间：
原始日志／产物／哈希／关联ID：
实际结果与差异：
结论：通过 / 失败 / 阻塞 / 未执行
缺陷及复测关联：
执行人／专业复核人／见证人：
```

MCP和Harness日志可能含业务输入输出；归档按项目资料权限管理，不把原始密钥放进配置摘要。当前脱敏识别已知凭据，不保证识别任意业务内容。只保留截图不足以重新计算指标；只保留JSONL也不能替代文件产物和专业审定。

### 冻结、打包和移交注意点

现有 `./package.sh` 生成 `dist/mc-tech-execution-0.1.0.tar.gz`及清单、校验文件。它会覆盖同名旧包，执行前先保存旧发布及其证据；源码或文档修改后新包必须重新取得哈希，旧搬运记录不能自动背书新包。部署包排除 `artifacts/`、日志、本机模型配置和运行数据，所以完整验收材料要作为独立证据包移交。交付前在干净目标环境解压、安装依赖并按手册完成代表任务，复核交付文件与冻结清单一致。

不符合项按规格书记录、通知和协商处理，整改后重新验证；保留原失败记录与新版本的关联。达到内部测试条件后进入甲方见证和评审，不能由开发人员仅凭测试脚本返回0自行宣布合同最终验收完成。
