竞品分析与小规模对照方案

用户为什么选择OpenMC Forge

核心问题：不要求用户说“用MCP”时，Agent会不会主动选它；选择之后，比直接SSH执行少了什么操作和错误。已有工程测试不能回答这两个问题。

先给判断

值得验证的产品价值是：把反复需要编程、检查和关联的OpenMC任务，变成可复用、可核对的操作。

科学算法来自OpenMC；MCP负责让Agent发现和调用；Skill解释何时用、怎样衔接。相同输入应算出相同科学结果，优势应表现为少写临时代码、少纠正、早发现错误和交付更完整。当前这些收益是有实现依据的假设，本轮观察到主动使用与一处临时数据加工错误，但完整任务尚未闭环，不能给出性能优劣结论。

当前普通折线图只证明样式和绘图出口可用，不能证明领域价值。若Agent通过SSH调用同一套CLI也一样方便，应承认价值主要来自工具包；若直接SSH同样可靠且更省事，就不应继续增加重复封装。

本轮实测：主动使用发生，但尚未证明整体更省事

不点名MCP的两次C组会话，都主动使用了领域工具；但没有一组完成全部交付，不能宣布MCP胜出。

更具体的发现：C组在结果读取后回到Shell临时编程，图和脚本都能生成，却把网格x/y对应转置了。相同StatePoint的工具包既有导出与原生分箱映射一致。这说明可复用的领域转换有价值，也说明仅“调过MCP”并不能保证最终交付正确。

预算、环境、偏差与原始证据

模型配置名claude-opus-5-5，来自现有DSH默认配置；不独立验证上游真实模型身份。采用已安装Windows DSH的ToolRuntime/LlmRuntime及MCP插件、通用WSL Shell桥；不是Desktop GUI完整会话，也不是反馈者的SSH-compute插件。用户明确确认先用同一WSL端比较。原服务与模型配置未改，新MCP测试实例为0.17.0，73个工具定义核对一致，测试退出确认进程及端口已清理。

共46次模型请求：临时客户端准备错误16次，六个干净会话各5次共30次。准备错误包括未解码工具参数字符串、Windows GUI进程未等待；均保留失败，不算产品缺陷。另两次临时服务就绪检测被环境代理影响，尚未进入模型调用；仅在测试进程设置loopback代理绕过后重做，未改配置。各次实际调用可从逐组result.json回查；没有用户点名“用MCP”。

原计划每会话最多8次；准备错误耗费预算后，剩余32次分成六个相同5次窗口，留下2次未用，不追加预算。故本轮不足以验证完整任务效率。部分流程在截止时仍有进展，不能标为产品能力失败；也不能用部分产物冒充完整交付。原始result中的“eight model requests”结束文案沿用旧字符串，实际请求数以network_requests、预算账本和调用记录为准。

六组原生输入和StatePoint指纹均保留；T2-C读取工具更新了副本中的results.json和.status-keff.json缓存，原生输入及HDF5未变。所有会话模型配置指纹核对不变。没有启动新求解，没有做物理验收。调用次数和Token只是原始观测，未达成同等结果，不能计算节省百分比。原始消息不保留模型私有思考内容或凭据。

一个足以区分“图生成了”和“数据用对了”的实证

以StatePoint的MeshFilter.bins逐项关联坐标，检查Agent导出的CSV：10000行中9900行的均值/标准差对应了另一个空间位置，仅对角线100格没有受转置影响。其脚本使用C顺序reshape后又转置显示，CSV坐标同样错配；100×100栅元图近似对称，外观难以察觉。工具包同一历史StatePoint的JSON按values[j][i]核对10000个均值全部一致。这个核对独立读取OpenMC原生分箱，不以工具包返回ok为依据。

Agent另把原始tracklength计分写成“per source particle per cm”；原始体计分flux单位应为particle·cm/source，按体积/功率换算需额外条件。这个错误出现在自行生成的metadata，不是MCP读取函数。依据：OpenMC官方计分与归一化说明。本包原有“raw tally、未换算功率或源强”避免了这次具体误写，但精确单位契约仍有改进空间，不能宣称所有单位错误已被工具阻断。

Agent提供的脚本在包外能运行，不依赖OpenMC；但可复现并不等于映射正确，换环境重画仍保留错误。其metadata未记录StatePoint SHA256。对照仅证明这一次已核验转换优于临时代码，不证明所有Agent必错或MCP协议使数值更准确。

公平比较三种方式

方式给Agent什么比较回答什么
A · Agent＋SSH-computeSSH能力、原生OpenMC、同一任务事实和官方API资料；允许自行编程。可正常读取SSH技能，不人为削弱。强Agent直接处理的实际基线。
B · Agent＋SSH＋工具包CLIA的条件，加同版工具包、CLI说明与等价任务指引；不连接MC MCP。B−A体现领域工具包、复用实现和工作流引导的合计收益。
C · Agent＋MCP＋同版工具包保留SSH作可选后备，同时连接MCP；同样可获得工作流指引，不在用户任务里点名MCP。C−B体现接口发现与调用方式的增益或代价；也观察是否主动选择。

本轮不单独宣称“Skill提升多少”：B/C共享相同领域指引，A保留正常SSH技能，比较的是实际使用组合。若以后需要拆分Skill贡献，再另做消融，不扩大本轮。

公平性与观察边界

同一宿主、同一模型及参数、相同初始输入、核数据与资源上限；各次新会话、独立目录，禁止前组结果流入后组。任务正文不出现MCP、CLI、工具名或“优先用工具”；只给科学目标、输入位置和交付要求。随机或轮换顺序，记录首轮启动、缓存冷热和安装耗时，安装不混进执行效率。

观察两层：①发现与引导是否真的进入模型请求；②模型怎样选择和完成。宿主丢失工具/指引属于接入失败，不伪装成模型不愿用；同时保留为实际产品体验问题。不得增加“必须用MCP”的隐藏规则后再宣称主动使用。不得索取或记录模型私有思考链，只记录可见请求、工具调用、结果与用户干预。

六次会话只用于初筛和定位，不足以给出普适成功率或统计显著性。真正因果归因及跨模型结论需要后续同输入重复；本轮不承诺。

判据：先正确完成，再比较负担

观察怎样记什么结论成立
不强制时主动选择C两次会话：首个领域动作是否用MCP、关键步骤实际路由、是否需要用户点名；发现/引导确实可见另留证。未点名即可选择并完成，才有主动选用的个案证据；只读environment不算任务主要经MCP完成。
正确完成T1/T2上述独立原生判据逐项通过；错误、未完成及预算停止原样登记。不能以更快抵销错量、错单位、源污染、漏计分或重复求解；任一关键项失败，不宣称该流程成熟。
少了哪些操作用户额外纠正次数；临时编写/修改的业务代码量；参数/路径试错及失败重试；模型请求/Token和总耗时。只报实际节省的步骤。内置同样复杂的操作仍记录，不把多次MCP调用藏成一次成功，也不直接以调用次数定输赢。
少了哪些错误无效引用是否在求解前发现；源输入/计分是否丢失；图表选择/误差/坐标/报告来源是否错误。A发生而B/C避免，才是本轮观察到的收益；A/B/C都正确，则只比较负担，不声称提升正确率。

完成输出只要一张六行表：方式、任务、可见性、主动路由、关键判据、额外纠正、临时代码、请求/Token、耗时、错误与证据目录。外加一句选择建议；不新建大套测试框架。

预先固定取舍：B优于A而C≈B，主推领域工具包、MCP作可选接入；C在同等正确性下进一步减少操作，才主张MCP体验优势；C需要反复提醒或调用链更繁琐，先改善发现与衔接；A稳定且更省事的任务保留SSH，不强迫走MCP。两条任务不足以外推所有科研场景。

模型预算建议及执行边界（尚未批准，不执行）

首轮六个新会话，每会话最多8次模型API请求（工具调用数量另记），合计最多48次，整体模型执行窗口最多30分钟，到任一上限停止。T1三组各最多一次真实求解，200粒子/12批/2非活跃批/单线程，每作业60秒上限；T2零求解。预算不足记未完成，不提高上限凑成功。

费用未知：使用者确认具体模型和单价后才能估算货币上限，不声称48次等于固定金额。复用现有配置但不修改；单独临时客户端及隔离工作区、临时MCP进程，先核对版本/完整工具定义/指纹，结束、失败、超时清理本轮进程。既有服务和数据不动，不自动安装/切换宿主、不追加请求。原计划阶段未调用模型；经用户批准已执行的实际结果和预算偏差见本页“实际对照结果”。

核心改进：交付一项完整科研任务，而不是暴露一堆函数

建议保留原子工具的灵活性，把默认指引和交付围绕三件事组织：模型变更到计算、已有结果到证据包、失败到确认后复算。先用现有Skill和数据把衔接做好；只有对照证明确有重复调用负担，再考虑聚合接口，不能先增加工具再找价值。

用户现在承担的工作改进方向与具体交付如何证明有用
Agent临时写改参、校验和进程管理，再由用户检查是否改对把明确科学条件落为新副本、实际参数差异、读回检查、提交快照和作业记录。用户先核对“改了什么”，不必读临时代码来猜。T1对照临时代码、额外纠正和错误拦截；独立读取XML/StatePoint。SSH同样做到就不记独有优势。
用户逐个问图从哪来、误差是什么、报告是否同一次计算一次交付同源图、完整数据、脚本和简短解释；先说明计分选择/坐标/归一化/误差，再给下载位置。报告已有来源能力，解释可由Skill组织；不宣称已自动生成全部解释。T2检查源/量/图/报告是否一致、是否重复求解、是否能包外改图，记录额外追问。
函数太多，Agent不断找工具，用户反复说“用MCP”让任务入口解释何时使用、最少必要参数和交接点。先检查指引是否到达模型；避免重复装Skill和先加载全套Schema。发现/路由通过后才优化调用长度。C组不点名MCP且保留Shell后备，观察实际关键步骤选择；不能用一次environment调用冒充主流程使用。

产品的核心承诺应是可重复的执行与可核查的数据交付。强Agent可以临时完成同样工作，但每次重新实现需要成本，也可能遗漏。只有对照看到这些成本或遗漏减少，优势才成立。MCP相对同包CLI的优势更窄：发现、参数组织和跨宿主调用；不赋予额外物理算法。

基于本轮的具体优先方案：①已有结果的交付优先复用现有绘图/导出，而不是把10000个值送进模型后再手写reshape；②结果的坐标映射、单位/归一化和来源由程序输出，Agent负责面向用户解释，避免凭文字再造数据口径；③若要新增功能，优先一个“指定作业和计分→生成同源结果包”的任务入口，内部组合既有读取/绘图/报告/清单，原子工具和脚本出口继续保留。第三项是新入口，必须另确认，本轮未实现。它的价值判据是少编排、少临时分析代码且保留同等可核对性，不是强制走MCP。

这次实际暴露了明确交接问题，后续应按它修改指引或任务入口，再用同一原生判据核对；不重复全套工程测试，也不把六次有限观察包装成竞品胜率。

优势如何落到用户能感受到的地方

绘图差异化：从“漂亮曲线”转为“可核查的科研结果”

配色、字体和线宽是基础质量，通用Agent也能做好。真正应展示的是：图上的位置和数值能对应计算对象，误差和不能解释的范围同时可见，结论能追到原始数据。独立脚本和数据保障用户自由调整，不争抢通用制图能力。

优先展示：空间计分＋不确定度

同一次计算的原始通量与相对标准差并排：既看“哪里贡献高”，也看“哪里估计更不稳定”。零贡献、缺误差和非有限值分别处理；真实坐标、层、能量选择与归一化随图交代。

现有C5G7样例：10000格、606格相对标准差>10%、最大约32.83%。只能说明这些格的统计精度需要谨慎，不能据此宣称物理错误或不合格。

其次展示：能量分箱与数据口径

谱图要能说明是箱积分值还是单位能宽谱、能量边界和单位是什么，多群计分是否对应MGXS群结构；不能把7个有效群渲染成500箱的精细物理谱。

已有能谱坐标/原始值和多群匹配告警可复用；自动重分群、专业谱解释不在现有样式交付内，不作为已完成功能宣传。
